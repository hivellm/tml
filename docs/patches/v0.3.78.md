# v0.3.78 — Shared-stdlib fast-path: gating bugs fixed, blocker model corrected (phase43a session 2, F-006/F-007)

**Date:** 2026-07-18

## Summary

phase43a had recorded four blockers preventing the shared-stdlib fast-path
(`build_stdlib_object`) from being enabled. Session 1 fixed blockers 1 and 2.
This session reproduced the fast-path for the first time and found the recorded
model was **wrong in both ordering and diagnosis**:

- Blockers 3 and 4 had never been *observed*, only inferred — everything sat
  behind a single bootstrap typecheck abort that aborted before any of it ran.
- Blocker 3's recorded root cause is **disproven**.
- Blockers 3 and 4 are **the same problem**.

Two real, independently-valuable bugs were fixed. The fast-path remains **OFF**;
one architectural blocker remains.

## Reproduction (no code edit required)

`tml test --unified` routes through the code path that already calls
`build_stdlib_object`. This makes the fast-path reproducible without the scratch
re-enable the task had assumed was necessary — the previous sessions' main
obstacle.

## Fixed

### 1. Phantom bootstrap imports (gating — nothing behind it had ever run)

`compiler/runtime/test_bootstrap.tml` named **12 modules by paths that do not
exist**. The first such import aborted typecheck, so `build_stdlib_object`
returned `""`, `g_stdlib_codegen_state` stayed null, and the fast-path never
engaged at all:

| Bootstrap wrote | Real module path |
|---|---|
| `core::mem` | `core::runtime::mem` |
| `core::clone` / `convert` / `cmp` / `marker` | `core::traits::*` |
| `core::pin` / `error` | `core::runtime::*` |
| `core::any` / `tuple` | `core::types::*` |
| `core::ringbuf` | `core::data::ringbuf` |
| `std::datetime` | `std::time::datetime` |
| `std::glob` | `std::file::glob` |

All 12 verified against disk **and** against real in-tree usage before editing
(`core::runtime::mem` has 66 uses across 55 files; `core::mem` has none).

### 2. `Unknown method: send_once` — private inherent-impl methods unregistered

**This is a latent GENERAL compiler bug, not a fast-path bug.**

The visibility filter in `types/env_module_load_decls.cpp` skipped private
methods of **non-generic, non-behavior** impl blocks, so they never entered
`types::Module::functions`. A public method calling a private sibling in the
same inherent impl — `HttpClient::send` → `send_once`
(`lib/std/src/http/client/client.tml:128`) — therefore had no `FuncSig`, and
`try_gen_module_impl_method_call` (`method_impl_module.cpp:272`) bailed out,
aborting the entire stdlib pre-compile.

It stayed latent because normal compilation defers library method bodies until
referenced (`decl/impl.cpp:411`) and no test calls `HttpClient::send`. Only
`library_ir_only=true` generates that body, which is why the fast-path work
surfaced it.

The fix **completes a pattern the same file had already applied twice** — to
free functions (~line 203: *"Register ALL functions (including private ones)…
The type checker already enforces visibility for user-facing imports"*) and to
generic/behavior impls (*"Private methods must be registered so they can be
found during generic method instantiation"*). Non-generic inherent impls were
the one case left behind.

## Corrected

### Blocker 3 — CLOSED AS MISDIAGNOSED

The recorded hypothesis ("`Range__I32` local vs cached `Range__I64` i64/i32
range-iterator width; resolve the index width from the registered signature")
is **disproven by reproduction**. The actual error is:

```
[K001] Failed to parse LLVM IR: '%tNNNNN' defined with type 'ptr' but expected 'i32'
```

`ptr` vs `i32` — **not** i64 vs i32, and not Range-related. Additionally the
register name recorded in the old notes (`%t9030`) is **not stable across
builds** (it is now `%t11353`, shifted by the blocker 1+2 fixes) and must not be
treated as an identifier. There is no separate range-width fix to land; writing
one would have been fixing a bug that was never there.

### Blockers 3 + 4 are the same problem (the one remaining, architectural)

With `library_ir_only=true`, the lazy-deferral guards at `decl/impl.cpp:411` and
`decl/func.cpp:647` are disabled, so the stdlib pass abandons reference-driven
emission and **eagerly compiles ~5000 library bodies that nothing has ever
exercised**. Codegen defects in never-compiled code surface only there — that is
the entire mechanism behind the "K001 under the fast-path" class, including what
was recorded as blocker 3.

The failing text lives in the **shared library body**: identical error in the
stdlib object and in all 14 per-file objects — one bug, not fourteen. Patching
the individual offending body is a treadmill; the next unexercised body fails
behind it. The durable fix is to make the stdlib pass emit the same
reference-driven set the normal path emits (the per-suite-scoped bootstrap +
F-007 decls-only/external-linkage linking).

Corollary: the flush loop at `generate_library_only.cpp:147-238` is **dead code**
in this mode — the same flag makes its stated job impossible.

## Measured

- Eager bootstrap: **968s** with `std::http`, **449s** without (the previously
  recorded ">500s" was an estimate). Note an earlier 939s figure was
  *time-to-abort* at `send_once`, not a completion time.
- Fast-path confirmed **engaging** for the first time
  (`Stdlib codegen state available`).
- Enabling it currently **fails the zero-divergence gate hard** — all 14
  core/hash tests fail. It must stay OFF until the scoped bootstrap lands.

## The treadmill is empirically demonstrated, not merely inferred

Three successive runs, each fixing/removing the current blocker, produced a
**different K001 in a different never-exercised body** each time:

| Run | Module set | Failure |
|---|---|---|
| 1 | full (incl. `std::http`) | `Unknown method: send_once` — *fixed* |
| 2 | `std::http` excluded | `'%t11353' defined with type 'ptr' but expected 'i32'` |
| 3 | full, `send_once` fixed | `'%t4937' defined with type 'i64' but expected '%struct.RawThread = type { i64 }'` |

Different module sets surface different latent defects, and each fix exposes the
next body behind it. This confirms the architectural diagnosis directly:
body-by-body patching cannot converge, because the fast-path compiles ~5000
bodies that no test has ever exercised. Only restoring reference-driven emission
(the scoped bootstrap) removes the class.

Note also that the codegen *state* is captured and the fast-path reports
"enabled" **even when the stdlib object fails to compile** — state capture is
independent of object compilation. Any enablement work must not treat "fast path
enabled" as evidence that the shared object is valid.

## Design constraint recorded for the remaining work

`group_into_suites` uses `max_per_suite = 1`, so a suite is effectively **one
file**. A literally per-suite bootstrap would build N bootstraps instead of 1 and
be **slower** — the state cache must be keyed on a **module-set hash** so files
with identical import sets share. `g_stdlib_codegen_state` / `g_stdlib_obj_path`
are single process-globals and must become a keyed map with its own
synchronization (up to 8 concurrent suite workers).

## Related latent defect found (worth its own task, not fixed here)

The eager emissions run with `in_library_body_ == false`, which enables Phase 4b
Str-temp auto-free **inside library bodies** — precisely what that flag exists to
prevent (`llvm_ir_gen.hpp`: *"Auto-freeing those temps causes use-after-free"*).
Not the cause of this K001, but real.

## Gate

Fast-path stays OFF; both fixes are verified against the clean-suite acceptance
set with the cold (cleared) meta cache:

| Suite | Result |
|---|---|
| core/hash | 14/14 |
| core/str | 33/33 |
| std/json | 23/23 |
| compiler/borrow | 12/12 |
| core/alloc | 43/44 (known floating concurrency miss, different test each run) |

`std/http`'s own 4 h2 `K001 integer constant must have integer type` failures are
**pre-existing** — documented as the phase27d `mut ref I64` breakage (commit
`b12aeebc`, already in HEAD), which is why `std/http` sits outside the acceptance
set. Confidence basis: documentary + the change being additive-only to a
registration table; not an empirical bisect.

**Cache note:** the fix changes `Module::functions` contents, which are
serialized into `.tml.meta`. Those caches are invalidated by *lib source*
timestamps, not by compiler changes, so `build/debug/cache/meta` must be cleared
after this change or the fix silently appears to do nothing.
