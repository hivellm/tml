# v0.3.30 — Pipe-hang fix (phase0r)

**Date:** 2026-04-16

## Summary

Fixes the long-standing hang reported by UzDB / MCP / CI agents where
`tml check`, `tml run`, and `tml build` would deadlock indefinitely when
stdout or stderr was redirected to a pipe or file. First P0 blocker from the
UzDB feedback letter is now resolved — AI agents and CI pipelines can run
the compiler non-interactively without losing output.

## Root Cause

Windows CRT defaults `stdout` to **full-buffered** mode when the stream is
redirected (non-TTY). The compiler emits a lot of diagnostic/log lines during
a single invocation: when cumulative output exceeds the 64 KB Windows pipe
buffer before a flush point, `tml.exe` blocks on `WriteFile` while the
parent reader is still waiting for more data to arrive. Classic
producer–consumer pipe deadlock.

Notably, `tml lint` never hung because it emits little output and fits in a
single buffer. That misdirection made the original bug report suggest
`WriteConsole` was the culprit, but the real issue was CRT buffering mode.

## Fix

`compiler/src/main.cpp` now switches `stdout` to **line-buffered** mode
(`_IOLBF`, 4 KB) when it detects the stream is not a TTY. Every `\n` now
flushes immediately, so the pipe is drained continuously instead of waiting
for a 4 KB chunk. `setvbuf` is called in `main()` before any I/O, per
C17 §7.21.5.6.

An `atexit` handler also flushes both streams on normal termination so no
output is lost. `stderr` remains `_IONBF` (as before) for crash visibility.

## phase1k — MCP subprocess timeout recovery

Fixes the other half of the UzDB/MCP hang: a subprocess spawned by
`mcp_tools.cpp::execute_command` that blocked WITHOUT writing any output
could never hit the timeout check, because the old implementation called a
blocking `ReadFile()` and only evaluated the deadline between reads.

Fix: replace the blocking read with a `PeekNamedPipe` poll loop (100 ms
interval). Each iteration either drains available bytes or ticks the
timeout budget and sleeps on `WaitForSingleObject(pi.hProcess, 100)`. If
the timeout expires, the process is terminated and we return exit 124
with a `[TIMEOUT]` marker. After the read loop exits cleanly, a bounded
`WaitForSingleObject` also kills any process that fails to exit within the
remaining budget — the previous unconditional `WAIT_INFINITE` was another
latent hang.

E2E validation: `compiler/tests/cli/mcp_timeout.sh` — 2/2 passing. A tight
outer `timeout 2` around `tml check valid.tml` returns in 0.72 s (same as
baseline 0.71 s) with exit 0; any regression would surface as exit 124.

## phase1j — Diagnostics-to-stderr audit

Audited every `std::cout` / `fprintf(stdout, …)` call site in `compiler/src/`
and confirmed that no diagnostic (error, warning, log) is emitted on stdout.
All diagnostic paths (`DiagnosticEmitter`, `log::ConsoleSink`,
`main_frontend.tml`) already route through stderr. The apparent "lost
diagnostics" reported by UzDB was a consequence of the pipe-buffer deadlock
(phase0r), not a stream-routing bug. With phase0r fixed, stderr flows
correctly through redirection.

Verified programmatically by `pipe_output.sh` cases 2, 3, 4, 8, 9.
