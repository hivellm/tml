# v0.3.75 — LRU cache eviction + import-driven meta loading (phase42c, F-031/F-036/F-019/F-032)

**Date:** 2026-07-18

## Summary

After phase42a/b made the incremental cache correct and bounded, two structural
wastes remained: **no eviction anywhere** (the LRU evictor was dead code with zero
call sites; `invalidate_all_exes()` cleared JSON fields but never deleted the EXE
files, so ~1.5k stale EXEs accumulated forever), and **eager whole-library meta
preload** re-read+hashed the entire lib source tree on every cold command
regardless of imports.

phase42c wires eviction, deletes stale EXEs, and adds a byte-identical mtime
fast-path to preload. The "replace eager preload with lazy per-import loading"
idea (F-036) and the "route `check` through QueryContext" idea (F-019) were both
**investigated and rejected** with concrete evidence — see below.

## Changes

### F-031 — LRU eviction wired + real EXE deletion (RESOLVED)

- New `cli::enforce_cache_caps()` → `evict_dir_to_cap()` (`cmd_cache.cpp`) LRU-evicts
  three content-addressed layers to configurable caps at **every test/build/run
  teardown** (`incr_test_run_end`, `build.cpp`, `builder_run.cpp` — separate from
  phase42a's incr/ir GC):
  - `tests/obj_cache` — 256 MB
  - suite `*.exe` files directly under `tests/` — 512 MB
  - `cache/run` — 128 MB
  - caps overridable via `TML_CACHE_OBJ_CAP_MB` / `TML_CACHE_TESTS_CAP_MB` /
    `TML_CACHE_RUN_CAP_MB`.
- The EXE evictor evicts **unreferenced orphans first** and files still referenced by
  `tests.json` **last** (reusable EXEs survive longest); sibling `.lib/.pdb/.exp/.ilk`
  are removed with each `.exe`.
- `TestResultCache::invalidate_all_exes()` now **deletes** the stale EXE files (and
  siblings) it clears — previously it only cleared the JSON `exe_path` fields, orphaning
  the files on disk forever. New `referenced_exes()` feeds the evictor's protect set.
- **Never** touches source, `build/debug/bin`, or the incr/ir store (phase42a owns that).

**Measured:** a post-rebuild run deleted 14 referenced stale EXEs via
`invalidate_all_exes`; a forced 100 MB cap evicted 890 unreferenced orphan EXEs
(503.25 → 99.80 MB reclaimed 403 MB) while the just-compiled referenced suite survived.
Steady state under default caps across consecutive clean runs: obj_cache 39 MB, run
52 MB, suite EXEs ≤ 94 MB — all bounded.

### F-036 — eager preload kept (byte-identical); mtime fast path added; full lazy REJECTED

The plan to replace eager `preload_all_meta_caches()` with lazy per-import loading was
**rejected — it cannot preserve byte-identical diagnostics.** The type checker, borrow
checker, and codegen resolve *unqualified* references (primitive impl methods with no
`use` like `s.len()`; library behaviors in generic bounds like `[T: Hash]`;
behavior-impls; type aliases) via **last-resort `GlobalModuleCache::get_all()` scans over
the whole library** (`env_lookups.cpp:156-162` — comment: *"populated by meta preload and
contains all library modules"* — `:190-196`, `:314-321`; `expr_call_method.cpp` ×5;
`checker_core.cpp:328`; ~9 codegen sites). A lazy subset (only `use`d modules + transitive
deps) leaves that cache partially warm → the scans miss modules → diagnostics diverge. The
parity set is effectively the whole library, not a stable <30-module prelude, so the
"<30 modules for a prelude-only file" target is unachievable without a large semantic change
(requiring explicit `use` for currently-implicit resolution) — not byte-identical. Per the
task's own precedence rule, byte-identical is the mandatory gate, so eager preload stays.

Instead the redundant-work half is fixed:

- **Directory-mtime "nothing changed" fast path** (`compute_lib_source_signature` +
  `.preload_stamp`, `module_binary_read.cpp`): stats (never reads) the lib source tree and,
  when the newest-mtime + file-count signature matches the last successful preload, **skips
  the per-module source read+CRC re-validation** — eliding the ~734-file staleness tax while
  loading the **identical** meta set into `GlobalModuleCache`. The stamp is written only after
  a full validation with nothing stale; `load_native_module` + `reset_meta_caches` still
  re-validate on actual use / lib-epoch change. Override with `TML_NO_META_FASTPATH=1`.

**Measured** (prelude-only `check`): full-validation preload ~419 ms vs fast-path ~285 ms
(~134 ms / ~32% off preload); 366 modules loaded either way; **0 diagnostic divergences
over a 25-file corpus** (fast-path vs full-validation).

### F-019 — routing `check` through QueryContext: REJECTED (ADR-010)

Document-blocked, not implemented. (1) No cross-process typecheck persistence — `force<>`
only reuses `CodegenUnitResult`, so one-shot `check` recomputes parse+typecheck anyway
(zero memo win). (2) No diagnostics replay + lossy contract — `TypecheckResult` flattens
errors to strings, drops cascading errors, has **no warnings field** (warnings are a
transient `TML_LOG_WARN` side effect), so any cache-skip silently drops diagnostics
(unsafe). (3) Redundant — the phase40a/42b daemon result cache already memoizes `check` by
argv-mtime + `universe_epoch` and replays the literal captured stdout/stderr/exit code. See
`docs/adr/ADR-010-check-query-routing.md`.

### F-032 — content-addressed cache keys (RESOLVED a+b)

- `generate_exe_hash` (`builder_helpers.cpp`) folds each object's **content** hash (streamed
  `crc32c_file`) instead of its **mtime** — a byte-identical relink is now a cache HIT while
  any real content change still invalidates.
- `generate_content_hash` migrated off `std::hash<std::string>` (64-bit, implementation-
  defined) to the shared **128-bit** CRC32C content fingerprint (`query::fingerprint_string`),
  deterministic across toolchains/builds. `generate_cache_key` still mixes the thread id (it
  is a temp-file disambiguator, not a content key — intentionally left).

## Gate

- **Eviction:** caps enforced (forced 100 MB → evicted to 99.80 MB; default caps hold
  naturally — obj_cache 39 MB, run 52 MB, suite EXEs ≤ 94 MB across consecutive runs);
  `invalidate_all_exes` deletes files. `compiler/tests/cli/cache_eviction.sh` 5/5.
- **Lazy-meta parity:** fast-path vs full-validation — 366 modules loaded both ways,
  **0/25 diagnostic divergences** (byte-identical). Note: the "<30 modules for prelude-only"
  target is documented as unachievable without breaking byte-identical (see F-036 above).
- **Zero test-result divergence:** clean suites identical across runs — core/hash 14/14,
  compiler/borrow 12/12, std/json 23/23 (matches the phase42a baseline). No codegen path
  touched (determinism gate N/A).
