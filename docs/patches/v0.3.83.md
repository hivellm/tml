# v0.3.83 — phase44a: test-dispatcher false-pass on panic

**Date:** 2026-07-19
**Task:** `phase44a_test-dispatcher-false-pass`
**Branch:** `fix/era0-stabilization`

A `@test` body that panicked was reported **`test_pass`**. Every test in the
project ran behind that hole, so the suite could not be trusted to report a
panicking test as failing. Found during phase26c, where it masked a real
codegen soundness bug and mimicked composition-sensitivity (the "standalone
passes / suite fails" split recorded in v0.3.80 was this harness defect, not
an IR difference — the IR was byte-identical and uniformly broken).

## Root cause

The **generated test-entry wrapper** called `tml_run_test_with_catch(...)`,
**discarded the result**, and ended with an unconditional `ret i32 0`. The
runtime caught the panic correctly, printed `panic: …` to stderr and returned
`-1` — which went nowhere, so the entry returned 0 and the dispatcher, which
branches correctly on the return code, dutifully emitted `test_pass`. The
dispatcher itself was innocent.

Site: `compiler/src/codegen/llvm/core/generate_entry.cpp` (discarded
`%test_catch_N`, then `ret i32 0`).

Tracing that path surfaced three further real defects on the same route:

- `MirCodegen::emit_test_entry_wrapper` called test bodies **directly** — no
  panic/crash catching at all, same unconditional `ret i32 0`.
- `tml_run_test_seh` wrapped the call in `__try/__except`; the panic `longjmp`
  had to unwind across that SEH scope and fastfailed with
  `STATUS_STACK_BUFFER_OVERRUN` (0xC0000409). The tell: the identical
  setjmp/longjmp in `tml_run_should_panic`, which had no SEH scope, always
  worked. VEH already handles crashes, so the `__try` was vestigial.
- `tml_run_with_timeout` never signalled the watchdog "done" event on a
  non-local exit, so the watchdog later fired `TerminateProcess(…, 99)` on an
  already-handled panic.

`@should_panic` was **entirely uncovered** — the only such decorators in the
repo were the new gate fixtures, and `lib/core/tests/convert/convert.test.tml`
carries a standing comment that the support is missing. It carried its own
small setjmp frame whose panic `longjmp` fastfailed; `tml_run_should_panic`
and `tml_run_test_with_catch` now share `tml_run_test_catch_impl(fn, quiet)`,
with `quiet=1` suppressing the `FATAL [runtime] panic:` line for an expected
panic (which is also what made the coordinator's stderr scan misreport it as
X003). A crash (`-2`) still does not satisfy `@should_panic`.

## Fix

- `generate_entry.cpp` — record the first non-zero result in `%fail_code`,
  fail fast, return it; added a per-test `i32()` thunk. The thunk is
  load-bearing: `tml_run_test_with_catch` takes an `i32(*)()` but
  unit-returning bodies are `void()`, so without it passing tests read a
  garbage i32 and fail.
- `mir_codegen.cpp` — MIR test bodies routed through `tml_run_test_with_catch`
  via the same thunk scheme, result propagated.
- `essential.c` / `.h` — removed the `__try/__except`; `tml_watchdog_cancel()`
  on every longjmp recovery path; added `tml_test_error_json()`; shared
  `tml_run_test_catch_impl`.
- `testing_dispatcher_gen.cpp` — `test_fail` now carries the real panic
  message; `name`/`file`/suite strings JSON-escaped.

**NDJSON contract change** (`docs/specs/10-TESTING.md` §11.2): `test_fail`
carries `error` with the actual panic message, and all string fields are
escaped. The stream was previously **invalid JSON** for any Windows path
(unescaped `\`); consumers that parsed it leniently now get conformant input.

**Deliberate narrowing:** the `__try/__except` fallback was removed rather
than preserved, on the basis that VEH runs first and the code's own comments
call SEH the superseded approach. If VEH ever declines an exception the
process now dies outright instead of returning `-2` — still a non-zero exit
and a reported crash, so it cannot resurface as a false pass.

## Fallout survey (item 1.3)

Ran alloc / collections / str standalone-per-file against the fixed compiler
to find what the false-pass had been hiding. Full evidence table:
`docs/analysis/phase44a-fallout/01-revealed-failures.md`.

- `core/alloc` **45/45**, `core/str` **33/33** — clean. Nothing was hidden
  where the original evidence came from.
- `std/collections` **100/103** — three files fail standalone-only and were
  **not** in `scripts/known-failures.txt`: `deque_extras.test.tml`,
  `deque_extras2.test.tml`, `iter_ref.test.tml`.

Those three are a **separate** bug, not this one: repeated isolated reruns of
the same file produce different failure modes (X002 timeout, HEAP_CORRUPTION
0xC0000374, 0xC0000409). Filed as
`phase44b_collections-standalone-heap-corruption`, grouped by root cause.

`iter_ref`'s 0xC0000409 raised a fair suspicion that it was residual fallout
of the SEH removal above. **Disproven by bisect:** restoring the
`__try/__except` behind an `#ifdef` and rebuilding reproduces the crash
identically. Corroborating — rewriting iter_ref's checks as return codes (no
panic, no longjmp anywhere) fails deterministically 6/6, with
`h.strong_count()` not returning to 2 after the by-value `iter()` copy drops:
a real refcount leak in the phase26e borrowing iterator. Recorded in phase44b
item 1.2 so it is not re-litigated.

Methodological note worth keeping: the 100ms watchdog fires first and reports
`TIMEOUT`, hiding the actual failure; under `@slow_test` the same binary
reaches the real 0xC0000409 after ~430ms. Part of the survey's
"timeout vs crash nondeterminism" is this masking, not heap-layout variance.

**Correction on core/alloc.** The implementing agents reported 45/45. Two
independent verification runs from the main session gave **43/45** and
**44/45**, each failing a *different* test (`allocator_ref_methods` +
`shared_sync_edge`; then `shared_getmut`) with `HEAP_CORRUPTION (0xC0000374)` /
exit `-1073740940`. This is the floating instability documented since v0.3.77
("every run fails exactly one randomly varying test via X002 timeout / X003
heap corruption"), **not** a phase44a regression — but 45/45 was a lucky run
reported as a stable result, and the honest baseline is 43–44/45.

Worth connecting: that signature is the same one isolated for phase44b —
panicking (or dropping) while a local `Shared` binding is live, i.e. drop glue
during unwind. The core/alloc floating flaky and the collections
standalone-only crashes are plausibly one bug, and phase44b should test that
hypothesis rather than treating them as two.
