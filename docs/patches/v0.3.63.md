# v0.3.63 — Remove the container field-drop leak special-case (phase26f 1.4)

**Date:** 2026-07-16
**Phase:** phase26f (Move-Semantics Activation Milestone) — item 1.4
**ADR:** ADR-009 (B1-on-AST) · rulebook decision #12

## Summary

`emit_field_level_drops` (`compiler/src/codegen/llvm/core/drop.cpp`) used to SKIP
field-level drops for struct fields of type `Heap`/`List`/`HashMap`/`Buffer`/
`BinaryWriter`/`BinaryReader`. The skip existed because — pre-move-semantics — a
struct assigned to another variable was bitwise-copied (not moved), so dropping a
container field would free a heap buffer still aliased by the copy = double-free.
The cost was a permanent **leak**: those container fields were never freed.

With fact-driven drop suppression landed (phase26f 1.3, v0.3.62), a struct moved
via a **tracked** site (let-init, by-value call arg, struct-literal init, `return`,
`..base`) has its SOURCE drop suppressed — so the surviving copy's field drop is
the ONLY one. Dropping the container field is now sound. **The skip is removed
entirely** (not narrowed), closing the F-022-style leak class for the drop shape
that actually fires (local `let` bindings dropped at scope exit).

## Risk analysis — untracked copy shapes (done before removal)

Removing the skip re-enables container field drops, so any copy shape whose source
drop is NOT suppressed could double-free. Enumerated and cleared:

- **(a) by-value METHOD args** — the fact side's safe-fallback (1.2b) does not set
  `moved_out` for method args. Covered on the double-free direction: the adversarial
  probe `container_field_methodarg_probe.tml` (container-bearing struct passed by
  value to a method, run under `TML_ALLOC_POISON`+`TML_ALLOC_QUARANTINE`) shows **no
  double-free** — its 2-leak residual is **identical before and after** the removal
  (pre-existing value-param/method-arg drop gap, not introduced here). Registered as
  the `tml_container_field_methodarg` corpus canary (15/15 adversarial).
- **(b) container read-outs** (`list.get`, `map.get`, …) — balanced clones since
  phase26b Step 3. Safe.
- **(c) iterator yields** — clones. Safe.
- **(d) raw `ptr_read[...]` in lib** — grep across `lib/core/src` + `lib/std/src`:
  every raw `ptr_read` yields a **primitive** (`I8`/`I32`/`I64`/`F32`/`F64`), never a
  handle-bearing struct. No untracked aggregate alias. Safe.

**Outcome: the special-case is FULLY REMOVED, not narrowed.** No shape required
restoring it.

## Leak-class closure (proof)

`scripts/fixtures/container_field_leak_probe.tml` — a `Box { items: List[I64] }`
constructed in a 500-iteration loop, held as a local `let` (the `List` source moved
into the field), dropped at loop-body scope exit:

- **Before removal:** 1000 leaks / 32000 bytes lost (every inner `List` buffer
  leaked).
- **After removal:** **0 leaks** — each buffer freed exactly once.

## Regression audit — the two apparent sync failures are PRE-EXISTING

`std/sync/mutex` and `std/sync/once_barrier` time out (X002) on the removed-skip
build. Root-caused by a controlled round-trip: **rebuilding with the skip RESTORED
reproduces the identical timeouts** — so these are pre-existing hangs in the
platform-mutex / Barrier+Condvar implementation (the `once_barrier` test file
already documents a known barrier hang inline), independent of drop codegen. They
are the "known-failures" the phase26f 1.4 gate excludes. None of `Mutex`/`RwLock`/
`Barrier`/`Once`/`OnceLock` has a container field in the skip set, consistent with
this being unrelated to the removal.

## Verification

- **Determinism corpus, both modes:** adversarial gate (poison+quarantine) **24/24**
  at/above floor — the container-heavy F-002/F-013/F-016/F-022 repros plus the new
  `tml_container_field_methodarg` double-free canary (15/15) are the double-free
  detector. Non-adversarial **22/23 at 100%** (the sole exception `essential.c`, the
  legacy cc_driver target at its documented 0% floor).
- **Libraries:** core/alloc **44**; core/str green; std/json green; core/sync green;
  std/collections at baseline (the `arraylist`/`class_coverage`/`collections_advanced`
  K001 family is the pre-existing phase27a `{i64,i64}`-vs-`i32` set, unchanged);
  std/sync only the two pre-existing hangs above.
- **Compiler sample:** `compiler/tests/compiler/memory` 7/7 (incl. `drop`),
  `partial_move_drop` pass, plus 40/40 struct/enum/generic/closure/dyn/move tests.
- **1.3 canaries still green:** `let_move_double_drop`, `refcount_bleed_userpath`.

## Not in this release

Items 1.5+ (drop-flag elaboration, fallout migration, final gates) remain open.
The value-param / by-value method-arg drop gap (fields of by-value params not
dropped at callee exit — the residual leak in the method-arg shape) is a separate
pre-existing limitation, out of scope here.
