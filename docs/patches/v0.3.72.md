# v0.3.72 — Test result cache revival + content-aware invalidation (phase41c, F-014/F-010/F-013/F-009)

**Date:** 2026-07-17 · **Branch:** `fix/era0-stabilization`

## Summary

The suite-level test result cache (`build/debug/cache/tests.json`) was supposed to
make an unchanged rerun near-free, but in the dominant workflow — compiler
development — it went cold on the first run after **every** build. Root cause and
fix are F-014 below; F-010/F-013/F-009 are result-transparent throughput cleanups
in the same test-compile path.

Scope boundary: this task owns the **test EXE cache / tests.json** side only. The
`incr.bin` red-green cache internals (compiler_build_hash, session load/save
semantics — F-024/F-020/F-023) are phase42a's and are **not** touched here; F-010
only batches the incr-cache *save* calls made from the test path.

## F-014 — the cache was dead across rebuilds (High)

**Root cause (measured, pre-fix binary):**

- `TestResultCache::compute_compiler_hash` fingerprinted the ~71 MB compiler DLL by
  **`mtime:size`**. mtime changes on every relink — and even on a bare `touch` —
  regardless of whether the emitted bytes (and therefore codegen behaviour)
  changed. Any change flipped the key, and the coordinator's `invalidate_all_exes()`
  cleared `all_passed`+`exe_path` on every entry. Proof: `touch tml_compiler.dll`
  then rerun `compiler/borrow` logged *"Compiler/runtime changed — invalidating all
  cached EXEs"* and took **17.1 s** (full recompile) vs 0.5 s cached.
- Second defect: `--no-cache` (and any filtered run) called `cache.save()` on an
  **unloaded** map, so a `--no-cache` single-suite run overwrote `tests.json` down
  to just that suite — measured a 319-entry cache reduced to 1.

**Fix:**

1. **Content-aware key** (`testing_test_cache.cpp`): the compiler hash is now
   `tml::VERSION` + CRC32C of the DLL **content** (+ file size), computed **once per
   process** (memoised via `std::call_once`; a long-lived daemon restarts on a DLL
   mtime change, so a memoised value never goes stale within one process). A no-op
   relink / `touch` that yields byte-identical output keeps the cache warm; any real
   codegen change still invalidates (correctness bias: content differs ⇒ invalidate).
2. **Always load before save** (`testing_coordinator.cpp`): the cache is loaded
   regardless of `--no-cache`, so `save()` preserves suites this run didn't touch.
   `--no-cache` now only disables *using* the cache to skip work (the partition step
   stays gated on `use_cache`), never destroys siblings.

"Cache what passed, recheck what failed" is preserved: `is_cached` still gates on
`all_passed`, and `get_reusable_exe` still reuses an unchanged EXE for a suite that
failed (skip recompile, re-run only).

**Measured (rebuilt binary, cold process each run, zero result divergence):**

| Suite | Run 1 (cold) | Run 2 (cached) | Parity |
|---|---|---|---|
| `core/hash` | 22.9 s | **1.84 s** | 14/14 → 14/14 |
| `compiler/borrow` | 18.5 s | **1.86 s** | 12/12 → 12/12 |
| `std/json` | 49.0 s | **1.85 s** | 23/23 → 23/23 |

| F-014 scenario | Before | After |
|---|---|---|
| `touch` DLL, rerun `compiler/borrow` | 17.1 s (invalidated, full recompile) | **1.9 s** (`is cached`, no invalidation) |
| `--no-cache` 1 of 3 cached suites | tests.json → 1 entry | **3 entries kept**, sibling still cached (1.8 s) |

## F-010 — incremental-cache saves serialized every suite worker (Medium)

Each test file did a global-mutex (`g_incr_cache_mutex`) load-merge-rewrite of the
whole `incr.bin` on save, serializing the otherwise-parallel suite workers. Each
file now folds its recorded entries into a **per-suite in-memory accumulator**
(`query::IncrCacheWriter`) under a cheap suite-local lock; the suite flushes
`incr.bin` **once** after its file loop, holding the global mutex for a single
write. Cross-suite serialization drops from O(files) to O(suites). New surface:
`QueryContext::merge_incremental_into(IncrCacheWriter&)` +
`IncrCacheWriter::merge_from_writer(...)` — **format-preserving**, does not change
the on-disk incr.bin layout or red-green semantics (that is phase42a). The heavy
IR/link payloads were already written per file during `codegen_unit()`; only
lightweight entry metadata is accumulated.

## F-013 — redundant per-file source scans (Low–Medium)

Each test file was reopened and re-read 2–3× (first 30 lines for conditional-runtime
registry synthesis, then the whole file for `use <pkg>::` build.tml detection). Now
each file's `use` imports are scanned **exactly once** up front into a per-file
`TestImportScan { use_lines, package_names }` that feeds both consumers. One
`getline` pass replaces the previous 2–3; behaviour is a superset of the old
(whole-file vs first-30-lines, comment lines skipped consistently).

## F-009 — 100 ms per-file codegen poll (Low–Medium)

The worker polled a done-flag every 100 ms while codegen ran on its own thread,
adding up to 100 ms of dead latency per file between completion and the next tick.
It now waits on a `condition_variable` (`wait_until` with the same 60 s deadline),
waking the instant codegen signals done. The codegen still runs on its own thread —
LLVM cannot be safely interrupted, so on timeout the thread is abandoned/detached; a
shared timer wheel would not remove this per-file thread, only the (now-eliminated)
polling, which is inherent to the F-008 single-threaded-codegen safety model.

## F-008 — per-file codegen still single-threaded (residual, documented)

phase41b deferred the codegen-state restructuring (F-006 root-caused but not landed —
the `g_stdlib_codegen_state` fast-path stays off), so the LLVM global-state constraint
that forces per-file codegen single-threaded is unchanged. Raising per-file
parallelism > 1 without that restructuring risks LLVM global-state corruption; per the
correctness bias it is left as-is (not raised).

## Tests

`scripts/tests/phase41c_test_cache.sh` — 4 end-to-end checks against the real
`tml.exe`: (1) second-run reuse + pass-count parity; (2) content-aware invalidation
(a DLL `touch` must not wipe the cache); (3) `--no-cache` preserves sibling entries;
(4) result transparency for a std-import suite (`std/json` identical cold vs cached).
Result: **4/4 pass**.
