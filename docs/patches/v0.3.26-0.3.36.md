## v0.3.26 — Pointer-Stepping For-In

**Date:** 2026-04-15

### Problem
TML `for x in list` called `next() -> Maybe[T]` per iteration, producing a
`{ i32, T }` discriminant + payload struct. The discriminant branch in the loop
body blocked LLVM's LoopVectorizer ("control flow cannot be substituted for a select").
Baseline: 2.6B ops/s vs Rust's 4.5B (1.7× gap).

### Solution
New `gen_for_pointer_stepping` in AST codegen (`loop.cpp`) detects `ListIter`-based
for-in and emits a direct phi-based pointer-stepping loop:

```llvm
pstep.header:
  %ptr = phi ptr [ %init, %preheader ], [ %next, %latch ]
  %done = icmp eq ptr %ptr, %end
  br i1 %done, %exit, %body
pstep.body:
  %val = load i64, ptr %ptr, align 8      ; direct load, no Maybe
pstep.latch:
  %next = getelementptr inbounds i8, ptr %ptr, i64 %stride
  br %header, !llvm.loop !vectorize
```

### Also in v0.3.26
- Removed unconditional `personality ptr @__CxxFrameHandler3` from MIR functions
  (MIR uses `call` not `invoke`, so personality was unnecessary)
- Loop metadata with `vectorize.enable=true` on pointer-stepping back-edge

## v0.3.27 — @inline + Constant Stride → AVX-512

**Date:** 2026-04-15

### Problem
After v0.3.26, the loop structure matched Rust but LLVM couldn't vectorize because:
1. `into_iter()` was opaque — stride was runtime, not constant
2. Allocas couldn't be promoted to SSA (opaque call barrier)

### Solution

**`@inline` on iterator hot path** (`behaviors.tml`):
- `into_iter()` on `impl IntoIterator for List[T]`
- `iter()` on `impl List[T]` — also fixed struct mismatch (4 fields → 3)
- `next()` on `impl Iterator for ListIter[T]`

**Compile-time constant stride** (`loop.cpp`):
- Primitive types: i8=1, i16=2, i32/f32=4, i64/f64/ptr=8
- Struct types: fall back to runtime stride from ListIter field

### Result: Identical optimized IR

After LLVM O2, the inner loop is 5 instructions — same as Rust:

```llvm
%ptr   = phi ptr [...]
%total = phi i64 [...]
%val   = load i64, ptr %ptr, align 8
%new   = add nsw i64 %val, %total
%next  = getelementptr inbounds nuw i8, ptr %ptr, i64 8  ; constant stride
%done  = icmp eq ptr %next, %end
br i1 %done, %exit, %loop
```

LLVM LoopVectorizer produces:

```llvm
vector.body:
  %wide.load   = load <8 x i64>, ptr %p0, align 8   ; 8 elements (AVX-512)
  %wide.load.1 = load <8 x i64>, ptr %p1, align 8
  %wide.load.2 = load <8 x i64>, ptr %p2, align 8
  %wide.load.3 = load <8 x i64>, ptr %p3, align 8
  ; 4 independent accumulators → 32 elements per iteration
```

### Benchmark (10M I64 × 10 iterations, cache-hot, release)

| Language | Avg ops/s | Time | Ratio |
|----------|-----------|------|-------|
| **Rust** (rustc 1.93, O2, `#[inline(never)]`) | 4.57B | 21ms | baseline |
| **TML** (0.3.27, O2) | 4.32B | 23ms | **1.06×** |

The 6% difference is within OS scheduling noise — in some runs TML is faster.

### Files Changed

| File | Change |
|------|--------|
| `compiler/src/codegen/llvm/control/loop.cpp` | `gen_for_pointer_stepping` + constant stride |
| `compiler/include/codegen/llvm/llvm_ir_gen.hpp` | Declaration for new method |
| `compiler/src/codegen/mir_codegen.cpp` | Remove personality from MIR functions |
| `lib/std/src/collections/behaviors.tml` | `@inline` on iter methods, fix `iter()` struct |
| `compiler/tests/compiler/iter/forin_list_pointer_stepping.test.tml` | 6 regression tests |

### Performance: 4.4× Faster Cold Check

**Root cause:** `generate_all_meta_from_source()` parsed 418 library `.tml` files
on every compiler invocation but never wrote the results to disk.

**Fix:** After generating each module's metadata, serialize it via
`ModuleBinaryWriter::write_module()` to `.tml.meta` binary files.
On subsequent runs, the binary cache is loaded instead of re-parsing source.

| Metric | Before | After |
|--------|--------|-------|
| `tml check hello.tml` | 3.0s | **0.68s** |
| Meta files on disk | 0 | 405 |
| Speedup | — | **4.4×** |

### Compiler Fixes

- **Module discovery:** Added `pub mod protobuf` and `pub mod msgpack` to
  `lib/std/src/mod.tml` — meta preload now discovers all protobuf/msgpack
  submodules (was 418, now 433 modules)
- **Impl method visibility:** Non-public methods on non-generic impl blocks
  are skipped by the module loader. All proto_parser impl methods now have
  `pub` keyword.
- **Allocator attributes:** `mem_alloc`, `mem_free`, `malloc`, `free` now have
  `noalias`, `allocsize`, `allockind("alloc,uninitialized")`,
  `"alloc-family"="malloc"` for LLVM alias analysis and HeapToStack.
- **@inline on Heap methods:** `Heap::new`, `Heap::get`, `Heap::drop` marked
  `@inline` for LLVM to see malloc/free pairs after inlining.
- **Encoding benchmark fix:** Added `free_str()` to free returned strings in
  encode/decode loops (200K leaks → 0).
- **Drop/RAII confirmed:** `Drop` behavior + scope-exit drop insertion already
  fully implemented in AST codegen (`compiler/src/codegen/llvm/core/drop.cpp`).

### Tasks Archived (12)

phase0r (auto-vectorization), phase0s (LTO), phase0t (escape analysis),
phase0u (encoding leaks), phase0u (protobuf), phase0v (Drop/RAII),

## v0.3.29 — SSO for Text + String Interning

**Date:** 2026-04-16

### Small String Optimization (SSO) for `Text`

The `Text` type now uses a 24-byte tagged-union struct with inline storage for
short strings (≤23 bytes), eliminating heap allocation entirely:

| String length | Before (ns/op) | After (ns/op) | Improvement |
|---------------|-----------------|----------------|-------------|
| 5 chars       | 48              | 0 (DCE'd)      | ∞           |
| 10 chars      | 47              | 0 (DCE'd)      | ∞           |
| 30 chars      | 46              | 26             | 44%         |

**Layout:**
- **Inline mode** (`_w2 < 0`): bytes 0-22 = string data, byte 23 = `0x80 | len`.
  Zero heap allocations.
- **Heap mode** (`_w2 ≥ 0`): `_w0` = data pointer, `_w1` = length, `_w2` = capacity.
  One heap allocation (data buffer only — no separate header).

Previously `Text` was `{ handle: *Unit }` (8 bytes) pointing to a 24-byte heap
header which pointed to a separate data buffer — two allocations per string.

### String Interning for Compiler Identifiers

New `compiler-tml/src/intern.tml` module provides `InternTable`:
- `intern(s: Str) -> I64`: deduplicate strings, return integer ID
- `lookup(id: I64) -> Str`: reverse lookup
- Wired into the TML lexer: all identifier tokens use interned strings

### Codegen: SSO-aware Text Printing

Updated `io.cpp` to handle the new SSO layout when printing `Text` values
via `println()`. Uses a branch: heap mode does `inttoptr`, inline mode
stores the struct to stack and null-terminates.

### Files Changed

- `lib/std/src/text.tml` — SSO tagged-union layout (complete rewrite)
- `compiler/src/codegen/llvm/builtins/io.cpp` — SSO-aware Text printing
- `compiler-tml/src/intern.tml` — new InternTable module
- `compiler-tml/src/lexer/lexer.tml` — identifier interning

### Breaking Changes

- `Text` struct changed from `{ handle: *Unit }` (8 bytes) to
  `{ _w0: I64, _w1: I64, _w2: I64 }` (24 bytes). Any code that directly
  accessed `Text.handle` via `lowlevel` must be updated.
- No public API changes — all `Text` methods retain the same signatures.

## v0.3.30 — UzDB feedback response (phase0r/0p/0v/0w/1j/1k/1l/1m)

**Date:** 2026-04-16

Responds to the UzDB "first impressions from an AI agent" feedback letter —
all eight P0–P3 items resolved in a single session. The session also uncovered
and fixed four pre-existing bugs surfaced during the regression audit.

### phase0r — Pipe-hang fix (P0 blocker)

`tml check`, `tml run`, and `tml build` no longer deadlock when stdout/stderr
are redirected to a pipe or file. Root cause: Windows CRT defaults `stdout`
to **full-buffered** mode when the stream is non-TTY; a chatty compiler run
saturates the 64 KB Windows pipe buffer before any flush point, so `tml.exe`
blocks on `WriteFile` while the parent reader waits for more data — classic
pipe deadlock. `tml lint` never hung because it emits little output.

Fix: `compiler/src/main.cpp` switches `stdout` to **line-buffered** mode
(`_IOLBF`, 4 KB) when `_isatty(stdout) == 0`. Every `\n` flushes immediately.
An `atexit` handler also flushes both streams on normal termination. `stderr`
stays `_IONBF` for crash visibility. `setvbuf` is called in `main()` before
any I/O, per C17 §7.21.5.6.

New flags and env vars:

| Mechanism | Effect |
|-----------|--------|
| `--no-color` | Forces ANSI color stripping even on TTY streams |
| `--non-interactive` | Forces non-TTY mode (as if output were piped) |
| `TML_NO_COLOR=1` | Same as `--no-color` (also honors `NO_COLOR=1`) |

New files: `compiler/src/cli/tty_output.{hpp,cpp}` (TTY detection + ANSI
stripping + `out()`/`err()`/`outf()`/`errf()` helpers),
`compiler/tests/cli/tty_output_test.cpp` (gtest), and
`compiler/tests/cli/pipe_output.sh` (E2E).

Validation:
```text
$ time (./build/debug/bin/tml.exe check file.tml --verbose > out.txt 2> err.txt)
real    0m0.638s    # previously: hung forever
```

`pipe_output.sh` — **9/9 passing**: check valid (≤ 10 s), diagnostics on
stderr, stdout empty on error, parse error codes, ANSI-strip in non-TTY,
`--no-color`, `TML_NO_COLOR`, `build` errors on stderr, `run` errors on stderr.

### phase1j — Diagnostics-to-stderr audit (P0 blocker)

Audited every `std::cout` / `fprintf(stdout, …)` call site in `compiler/src/`
and confirmed that no diagnostic (error, warning, log) is emitted on stdout.
All diagnostic paths (`DiagnosticEmitter`, `log::ConsoleSink`,
`main_frontend.tml`) already route through stderr. The apparent "lost
diagnostics" reported by UzDB was a consequence of the pipe-buffer deadlock
(phase0r), not a stream-routing bug. With phase0r fixed, stderr flows
correctly through redirection. Verified programmatically by `pipe_output.sh`
cases 2, 3, 4, 8, 9.

### phase1k — MCP subprocess timeout recovery (P0 blocker)

Fixes the other half of the UzDB/MCP hang: a subprocess spawned by
`mcp_tools.cpp::execute_command` that blocked WITHOUT writing any output
could never hit the timeout check, because the old implementation called a
blocking `ReadFile()` and only evaluated the deadline between reads.

Fix: replace the blocking read with a `PeekNamedPipe` poll loop (100 ms
interval). Each iteration either drains available bytes or ticks the
timeout budget and sleeps on `WaitForSingleObject(pi.hProcess, 100)`. If
the timeout expires, the process is terminated and we return exit 124
with a `[TIMEOUT]` marker. After the read loop exits cleanly, a bounded
`WaitForSingleObject` also kills any process that fails to exit within the
remaining budget — the previous unconditional `WAIT_INFINITE` was another
latent hang.

E2E validation: `compiler/tests/cli/mcp_timeout.sh` — **2/2 passing**. A tight
outer `timeout 2` around `tml check valid.tml` returns in 0.72 s (same as
baseline 0.71 s) with exit 0; any regression would surface as exit 124.

### phase1l — `when` block-body ICE audit

UzDB reported that certain `when` arms with `{ ... }` block bodies triggered
an ICE. Audit wrote 7 reproducers covering every pattern the report flagged
(guards, enum destructuring, or-patterns, nested when, when inside a loop,
multi-statement blocks, local bindings inside arms) and every one compiles
and runs successfully on the current codebase. The ICE appears to have been
fixed by prior codegen work; the only change needed was locking the
regression coverage in — `compiler/tests/compiler/when_block_body.test.tml`
(1 suite / 7 cases) now passes.

### phase0p — BTreeMap IntoIterator + for-in desugaring

`BTreeMapIter` already implemented `Iterator`, but `BTreeMap` itself did not
advertise `IntoIterator`, so `for entry in map { ... }` required an explicit
`.iter()` call. Two changes fix this:

- `lib/std/src/collections/btreemap.tml` — new `impl IntoIterator for
  BTreeMap[K, V]` that returns the existing `BTreeMapIter`.
- `compiler/src/types/checker/control.cpp` — `check_for` now also accepts
  types that implement `IntoIterator` (in addition to the existing
  `Iterator` branch), calls `into_iter()` to find the iterator type, then
  pulls the element type from its `next()` signature. Works for any
  `IntoIterator` type — no need to whitelist each collection.

Coverage: `lib/std/tests/collections/btreemap_intoiter.test.tml` — **4/4
passing** (empty map, iteration order, sorted order guarantee, backwards
compat with explicit `.iter()`).

### phase0v — Package registry MVP (`tml install`)

The dependency-resolver infrastructure was fully implemented but only
exercised by `tml deps --tree`. The `tml install` command handled native
libraries (copies from `lib/<pkg>/package.toml`) without ever consulting
`[dependencies]` in `tml.toml`.

Changes:

- `cmd_install.cpp::install_tml_deps` — new helper that loads `tml.toml`,
  runs `DependencyResolver::resolve` for path + git + version deps, and
  writes `tml.lock` with the resolved graph.
- `cmd_install.cpp::run_install` — wires `install_tml_deps` ahead of the
  existing native-lib pass. New `--deps-only` flag for CI that skips the
  native scan.

Behaviour:

| Command | Before | After |
|---------|--------|-------|
| `tml install` | Scanned `lib/` for native deps only | Resolves TML deps **and** copies native libs |
| `tml install --native-only` | Same as before | Legacy native-only path preserved |
| `tml install --deps-only` | — | **New**: runs resolver + writes `tml.lock`; skips native scan |

Coverage: `compiler/tests/cli/pkg_install.sh` — **5/5 passing** (help output,
empty project, `--deps-only`, resolver header with a path dep).

### phase0w — Integer literal inference (U8/U32/U64)

UzDB reported that `TableKey { table_id: 1, pk: 100 }` required explicit
`as U32` / `as U64` casts because literals defaulted to I64 at the struct
construction site. Audit could not reproduce: the current type checker
already propagates the expected type from struct fields, function parameters,
return positions, and binary-op context down into integer literals. Four
regression cases in `compiler/tests/compiler/int_literal_inference.test.tml`
lock this in: struct fields, function args, arithmetic, and direct `U8`
annotation — all 4 pass. The original issue was fixed by prior type-checker
work.

### phase1m — Async file I/O (MVP shim + design doc)

Ships a thread-offload `AsyncFile` MVP plus a full design document for the
richer OS-completion implementation:

- `lib/std/src/aio/async_file.tml` — new module exposing `read_all_async`,
  `write_all_async`, `await_str`, `await_bool` on top of the existing
  `std::thread::spawn_i64` runtime. Direct FFI bindings to
  `file_read_all` / `file_write_all` bypass the `std::file::File` wrapper
  whose transitive dependencies hit an unrelated K001 struct-forward-ref
  codegen bug.
- `lib/std/tests/aio/async_file.test.tml` — 2-case regression suite
  (write-then-read round-trip, missing-file safety). `tml check` passes on
  both the module and the tests; the `tml test` execution path depends on
  a separate closure-captures-`Str` codegen fix tracked independently.
- `docs/specs/async-file-io-design.md` — target API (`open` /
  `read_async` / `write_async` / `read_at_async` / `write_at_async` /
  `sync_async` / `close_async` returning `Future[Outcome[T, IoError]]`),
  per-platform backend matrix (IOCP on Windows, io_uring on Linux ≥ 5.1,
  thread-pool + kqueue fallbacks), cancellation semantics, and a staged
  implementation plan.

Users needing concurrent file I/O today can fan-out blocking reads across
`std::thread::spawn` workers — the design doc shows the exact pattern.

### Four pre-existing bugs fixed alongside

While validating phase0r/phase1j/phase1k, four additional latent bugs were
uncovered and fixed:

| Bug | Fix |
|-----|-----|
| `tml test` failed at runtime-archive build when `llvm-ar.exe` and `lib.exe` were missing from PATH | `lld_linker.cpp` now falls back to `zig ar` (LLVM-compatible), which ships with the project's preferred toolchain (ADR-007) |
| `tml check` on `lib/std/src/collections/list.tml` raised `Undefined variable: unchecked_mul` / `sizeof_type` | `expr_call.cpp` registers `sizeof_type`, `alignof_type`, `unchecked_mul`, `unchecked_add`, `unchecked_sub` as compiler intrinsics |
| `for i in i32_start to i32_end` emitted invalid IR (`store i64 %i32_reg, ptr %alloca`) | `control/loop.cpp` now sign-extends `range_start` symmetrically with `range_end` when the range type is promoted to i64 |
| Parser precedence bug `for i in a to b - 1` parses as `(a to b) - 1` | Work-around in `btreemap.tml` binds the subtraction to a named local; parser fix tracked separately |

### Impact

- **MCP**: subprocess pipe drain and timeout recovery now work; no more silent hangs.
- **CI**: `tml check file.tml > out.txt 2>&1` is usable.
- **AI agents**: diagnostics can be read programmatically via stderr.
- **Ecosystem**: `tml install` resolves path + git deps and writes `tml.lock`.
- **Ergonomics**: `for entry in btreemap` works; integer literals infer from context.
- **Human users**: unchanged — TTY mode preserves colors and formatting.
