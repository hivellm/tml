# v0.3.77 — Auto-deref `ref` operands in binary operators (phase27d)

**Date:** 2026-07-18

## Summary

Binary operators now read through `ref` / `mut ref` operands in value context, in both
the type checker and **both** codegen paths. Previously `count + 1` / `count >= max`
where `count: mut ref I64` was rejected with `T001` ("requires matching types, found
mut ref I64 and I64") plus a knock-on `T056`, even though assignment-through-`mut ref`
and unary deref were already supported.

**phase27d was NOT a regression.** It was initially filed as one (suspected fallout from a
concurrent session's uncommitted codegen/parser work), but investigation showed the
failing construct never worked: the errors are emitted by the **type checker**, which does
not run codegen at all, and they reproduce on the committed binary with no uncommitted
changes applied. The root cause is a long-standing **committed gap** — `check_binary` had
no `ref` unwrapping, unlike `check_unary`'s deref handling and the
assignment-through-`mut ref` allowance right beside it. The `std/http` sources that
surfaced it were correct all along.

## The two halves

Fixing only the checker moves the error from check-time to compile-time rather than
resolving it, so both halves ship together. Landing the checker change alone would leave
a check/codegen divergence — code that type-checks but cannot be compiled — which is
strictly worse than the original error.

### 1. Type checker — `compiler/src/types/checker/expr_ops.cpp`

`check_binary` gains a `deref_ref` helper that resolves an operand and unwraps `RefType`
to its `inner`. Applied in three places:

- **Compatibility check + error text** (`check_binary_types`) — `mut ref I64` now compares
  as `I64`.
- **RHS expected-type propagation** — `check_expr(*binary.right, deref_ref(left))`, so an
  unsuffixed literal RHS infers the pointee type (`I64`) rather than `mut ref I64`.
- **Arithmetic result type** — `Add`/`Sub`/`Mul`/`Div`/`Mod`/`BitAnd`/`BitOr`/`BitXor`/
  `Shl`/`Shr` return `deref_ref(left)`.

`PtrType` is deliberately left intact so genuine pointer arithmetic keeps its pointer
result, and comparisons keep returning `make_bool()`.

### 2. Codegen — load through the reference

Codegen must now agree with the checker's deref'd result type, or it passes a pointer
where a scalar is expected.

**AST / legacy path** (`expr/binary_ops.cpp`, `expr/core.cpp`, `llvm_ir_gen.hpp`).
`mut ref` primitives already auto-deref'd in `gen_ident`; immutable `ref` did not, so
`n < 100` (`n: ref I64`) emitted `icmp slt i32 %ptr, 100`. Immutable `ref` now derefs
too, but **only when the consumer opts in** via the new `deref_ref_in_value_context_`
flag, which `gen_binary_ops` sets around a **direct identifier** operand.

The opt-in is required rather than unconditional: unlike `mut ref`, a bare `ref` local is
routinely passed straight through to another `ref` parameter — e.g. `PartialEq`'s default
`ne(this, other: ref Self) = not this.eq(other)`. Those call sites want the pointer, and
the method-call argument path has no `local_is_ref` bypass (only `call_user.cpp`'s
free-function path does), so an unconditional deref emitted a bogus `inttoptr` for
integers and outright invalid IR for floats (`call i1 @...F32..eq(float %this, ptr %t)`).
Scoping the flag to a direct identifier operand also keeps it from leaking into nested
expressions.

**MIR path** (`mir/thir_mir_builder.cpp`, `mir/thir_mir_builder_expr.cpp`). The MIR
pipeline had the same gap plus three more, all previously unreachable because the
construct never type-checked:

- `build_binary` — operands whose THIR type is `RefType` now get a `LoadInst`; without it
  the emitted IR was `icmp sge ptr %count, %max`. `PtrType` is left intact, matching the
  checker.
- `build_binary` result type — an arithmetic node whose THIR type is still `ref T` now
  produces `T`. This matters beyond the instruction itself: `MergeReturnsPass` types the
  unified-exit phi from `InstructionData.type`, so leaving `ref I64` emitted
  `phi ptr` in an `i64`-returning function.
- `build_assign` — assigning to a `mut ref` binding now emits a `StoreInst` through the
  pointer instead of rebinding the SSA name, so the caller observes the write
  (`bump(mut ref c, 10)` previously left `c` unchanged).
- `build_unary` — `mut ref <local>` now yields the address **of the variable**. The
  generic ref path allocas a temporary and stores a copy, so writes through the reference
  landed in the temporary. The variable is instead promoted to alloca-backed storage
  (`mut_struct_vars`) the first time its address is taken, and `build_var` loads through
  that alloca for scalars as well as aggregates — guarded on the binding not itself being
  a `ref`, since a `ref` parameter holds the pointer as its value.

## Verification

- New fixture `compiler/tests/compiler/basics/mut_ref_value_context.test.tml` — `mut ref`
  comparison + arithmetic + write-through, and immutable `ref` read-only arithmetic.
- Runtime behaviour verified on **both** codegen paths (MIR and `--legacy`), all six
  observed values correct including caller-visible write-through.
- Zero divergence on the phase27d gate suites: `core/hash` 14/14, `compiler/borrow` 12/12,
  `std/json` 23/23, `core/str` 33/33.
- `scripts/determinism-gate.sh 10` → 28/28 targets at or above their baseline floor.
- `check` on `lib/std/src/http/app/app.tml` (was 7 errors) and
  `lib/std/src/http/server/parse.tml` (was 3) both clean, 0 occurrences of "found mut ref".

Also included: `lib/std/src/http/server/parse.tml` renames a local `match` (a reserved
word) to `matched`.

## Pre-existing failures confirmed unrelated

Two classes of failure were observed during gating and proven pre-existing by rebuilding
with the change neutralized and re-testing:

- `compiler/tests/compiler/cc_int_main.test.tml` and `cc_with_stdio.test.tml` — identical
  `K001 use of undefined type named 'struct.EventEmitter'` at `ir:143`, in the type-definition
  preamble emitted before any function body.
- `core/alloc` Shared/Sync tests — every run fails exactly one *randomly varying* test
  (`shared_getmut`, `shared_refcount`, `shared_sync_edge`, `sync_get_accessors`,
  `shared_try_unwrap_weak`, …) via `X002 TIMEOUT` or `X003` heap corruption. A matched
  7-run sample on both builds showed the same distribution.

Note also that the `condmove` determinism targets dip below their 100% floor roughly one
gate run in two, on a different target each time; the probes pass 30/30 when run directly.
