# v0.3.47 — C-frontend parser: skip MSVC `__declspec` / GCC `__attribute__` (phase0z, partial)

**Date**: 2026-05-02
**Branch**: `feat/self-hosting-compiler`
**Task**: phase0z_cc-driver-essential-c-residual

## TL;DR

`cc_driver` previously bailed on the very first MSVC compiler-extension
attribute it encountered while parsing `essential.c`. This patch teaches
the C parser to skip MSVC `__declspec(...)`, GCC `__attribute__((...))`,
and ~17 other bare extension keywords so real-world Windows C headers
parse cleanly. essential.c now advances past
`compiler/runtime/diagnostics/backtrace.h:261` (the `TML_EXPORT` macro
expansion). The full self-compile remains gated on a separate non-
deterministic SIGSEGV in the parenthesized inner-declarator path —
filed as follow-up `phase24h_cc-funcptr-typedef-sigsegv`.

## Bug A — Parse failure on `__declspec(dllexport)` — FIXED

### Reproduction

```bash
$ cmd /c "build\\debug\\cc_driver.exe compiler\\runtime\\core\\essential.c -I compiler\\runtime\\include\\c-stdlib --emit=ast"
... 48504 leaks ...
cc_driver: parse failed
```

The error message was opaque (no position, no construct). First diagnostic
step: improve the error report. Patched `cc_driver.tml` to surface the
raw `CParseError`'s file/line/col + message, AND mirror it to
`.sandbox/cc_driver_lasterr.log` so the error survives stdout/stderr
buffering crashes (the bash mingw redirect path SIGSEGVs before flush).

Recovered:

```
cc_driver: parse failed at compiler/runtime/core/../diagnostics/backtrace.h:261:20: expected type specifier
```

`backtrace.h:261:20` is `__declspec(dllexport)` inside the `#ifdef _WIN32`
branch of the export macro definition. The TML cc preprocessor defines
`_WIN32=1` (predefined.tml:30), so the `__declspec` token reaches the
parser as an `Ident`. `cp_parse_specifiers` then bails because
`__declspec` is not a known specifier keyword.

### Root cause

`compiler-tml/src/cc/parser.tml::cp_parse_specifiers` (line 369) loops
over tokens and routes by `CTokenKind`. The `Ident` arm only matches
typedef names; any other identifier breaks the loop. With no specifiers
consumed and `p == pos`, line 407 raises `expected type specifier`.

### Fix

Added `cp_skip_attribute_specifiers(parser: CParser, pos: I64) -> I64`
which skips contiguous runs of:

- `__attribute__((...))` (GCC double-paren)
- `__attribute(...)` (legacy single-paren variant)
- `__declspec(...)` (MSVC)
- Bare keywords: `__cdecl`, `__stdcall`, `__fastcall`, `__thiscall`,
  `__vectorcall`, `__forceinline`, `__inline`, `__inline__`,
  `__restrict`, `__restrict__`, `__extension__`, `__volatile__`,
  `__const`, `__const__`, `__signed`, `__signed__`

Helper `cp_skip_paren_group` walks balanced parens with depth counting;
returns the original position on unbalanced input so the caller bails
without an infinite loop.

Called at the top of every `cp_parse_specifiers` loop iteration so
attributes interleaved with real specifiers (e.g.
`static __forceinline int f(...)`) are also handled.

### Bonus partial fix at the typedef-registration site

`cp_parse_top_decl` line 1722-1728 used `name` twice without
duplicating: once in `parser.typedefs.set(name, 1 as I64)` and once
in the `CTypedefDef` literal. Because `HashMap.set(this, key: K, ...)`
takes the key by value, the parameter's drop at end-of-callee may free
the Str buffer the caller's `name` also references. Added
`name.duplicate()` on the `set` call. This is a partial mitigation —
the underlying convention (HashMap `set`/`has`/`get` taking the key by
value) needs a deeper fix, tracked under phase24h.

### Regression tests

Added 3 tests to `compiler-tml/tests/native/c_parser.test.tml`:

- `test_parser_skip_declspec_dllexport` — `__declspec(dllexport) int x;`
- `test_parser_skip_attribute_noreturn` — `__attribute__((noreturn)) void abort_now();`
- `test_parser_skip_bare_forceinline` — `static __forceinline int x;`

All 3 pass after fresh `tml test --suite=other --filter=c_parser`
(46021ms total, 1 suite with 40 @test functions).

## Bug B — Non-deterministic SIGSEGV under redirected stdio — DIAGNOSED, NOT FIXED

### Reproduction

```bash
$ for i in 1 2 3 4 5; do
    ./build/debug/cc_driver.exe compiler/runtime/core/essential.c -I compiler/runtime/include/c-stdlib --emit=ast > /dev/null 2>&1
    echo "exit=$?"
  done
```

Result: 4/5 SIGSEGV (exit 139), 1/5 exit 1 with the parse error. The
crash rate is sensitive to heap layout and stdio buffering; identical
invocations produce different exit codes across runs.

Bisection found the SIGSEGV is not stdio-related but tied to the
**parenthesized inner-declarator path** in the parser:

- `int *p;` (no parens) — 10/10 exit 0.
- `int (*p);` (paren'd pointer declarator) — ~30% SIGSEGV.
- `typedef void (*sig_t)(int);` (function-pointer typedef) — ~60% SIGSEGV.
- `typedef int (*hook_fn)(int); static hook_fn x;` — sometimes
  `hook_fn not a typedef` parse error (typedef registration corrupted
  by the same bug class), sometimes SIGSEGV, sometimes OK.

### Root cause class

Same Heap-borrow-drop bug class as phase24c/24d/24e/24f/24g. The
parenthesized-inner-declarator path goes through partial-field-move
patterns twice (once in inner recursion at `cp_parse_direct` line 1246
`leaf = inner.decl`, once in outer `cp_parse_declarator_inner` line 1338
`var d = direct.decl`), then through `Shared::new(d)` move-then-reassign
at line 1341. TML codegen's drop chain on the source struct may
double-drop moved-out fields when the recursion depth + Shared payload
combination triggers it.

phase24f and phase24g already migrated the bulk Heap chains to
`Shared[T]`; the remaining crash is in the partial-field-move pattern
that phase24g intentionally left in place because it requires either
TML compiler-side codegen support for partial-move tracking, or a
broader value-passing convention change.

### Why this is not fixed in v0.3.47

Per task instructions: "If the missing construct is large-scope, do
NOT attempt to implement it here. Document the gap clearly, file a
follow-up task, and STOP." The structural fix requires either:

1. TML compiler codegen support for partial-field-move tracking (so
   the source struct's drop skips moved-out fields).
2. Continued migration of `CParsedDeclarator` and `CDeclarator`
   value-passing chains to `Shared[T]` (phase24g continuation).
3. A change to `HashMap[Str, V].set/has/get` to avoid value-passing
   the key on every call.

All three are out of scope for a "parse failure" task. Filed as
follow-up `phase24h_cc-funcptr-typedef-sigsegv` with full diagnostic
notes and minimal repros.
