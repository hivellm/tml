## v0.3.20 — Fix K001 Struct Forward-Reference in LLVM IR

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Fixes the K001 `undefined type named 'struct.EventEmitter'` error that
blocked all `std::file` tests and any code importing the stream/events
modules. The root cause was that `llvm_type_from_semantic` returned
`%struct.Name` references without ensuring the struct type definition
had been emitted to the IR. When struct A (e.g., `ReadableStream`)
referenced struct B (e.g., `EventEmitter`) from a different module,
B's type definition was missing.

## Changes

### `compiler/src/codegen/llvm/core/llvm_types.cpp`

**`llvm_type_name()`** — the central type name resolution function now
searches the module registry for unknown struct types and emits their
definitions on-demand before returning the `%struct.Name` reference.

- Searches both `mod.structs` and `mod.internal_structs` in all loaded modules
- Registers the struct in `struct_types_` BEFORE processing fields to break
  cyclic references (A→B→A)
- Uses `thread_local` re-entrancy guard (`resolving_types` set) to prevent
  infinite recursion

**`llvm_type_from_semantic()`** — the non-generic NamedType fallback now
delegates to `llvm_type_name(named.name)` instead of directly returning
`"%struct." + named.name`, ensuring the on-demand emission logic runs.

## Impact

- All `std::file` tests can now compile (previously blocked by EventEmitter K001)
- Any cross-module struct references that caused forward-reference errors are fixed
- Compiler test suite: 156/157 (only pre-existing `let_patterns` X002 timeout)

## v0.3.21 — U128/I128 Display Formatting

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Adds `to_string()` for `U128` and `I128` types via `impl Display`. Pure TML
implementation using repeated division by 10 — no C runtime needed.

Requested by the UzDB AI agent for logging 128-bit `ConnectionId` values.

## API

```tml
let id: U128 = 340282366920938463463374607431768211455
println(id.to_string())  // "340282366920938463463374607431768211455"

let neg: I128 = -42 as I128
println(neg.to_string())  // "-42"
```

## Changes

### `lib/core/src/fmt/helpers.tml`

- `u128_to_str(value: U128) -> Str` — allocates 40-byte buffer, writes digits
  backwards via `% 10` / `/ 10` loop, returns pointer to first digit.
- `i128_to_str(value: I128) -> Str` — handles sign; uses two's complement
  negation (`0 - raw as U128`) for absolute value (handles I128::min correctly).

### `lib/core/src/fmt/impls.tml`

- `impl Display for U128` — delegates to `u128_to_str`
- `impl Display for I128` — delegates to `i128_to_str`

## v0.3.22 — std::msgpack (MessagePack Binary Serialization)

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Adds `std::msgpack` module — a pure TML implementation of the MessagePack
binary serialization format. Same data model as JSON but 2-5x smaller on
the wire and faster to encode/decode. Requested by UzDB for their database
client/server binary protocol.

## API

```tml
use std::msgpack::{MsgPackWriter, MsgPackReader}

// Encode a map with two entries
var w: MsgPackWriter = MsgPackWriter::new()
w.write_map_header(2)
w.write_str("name")
w.write_str("TML")
w.write_str("version")
w.write_u64(322 as U64)
let data: Buffer = w.to_buffer()

// Decode
var r: MsgPackReader = MsgPackReader::from_buffer(ref data)
let n: I64 = r.read_map_header()      // 2
let key1: Maybe[Str] = r.read_str()   // Just("name")
let val1: Maybe[Str] = r.read_str()   // Just("TML")
```

## Module Structure

```
lib/std/src/msgpack/
  mod.tml     — module root, public re-exports
  types.tml   — MsgPackType enum, MsgPackError enum
  writer.tml  — MsgPackWriter encoder (Buffer-backed)
  reader.tml  — MsgPackReader decoder (cursor-based)
```

## Encoder (`MsgPackWriter`)

Full MessagePack spec coverage:
- `write_nil()`, `write_bool(Bool)`
- `write_u64(U64)`, `write_i64(I64)` — auto-selects compact encoding
- `write_f32(F32)`, `write_f64(F64)`
- `write_str(Str)` — fixstr/str8/str16/str32
- `write_bin(ref Buffer)` — bin8/bin16/bin32
- `write_array_header(I64)`, `write_map_header(I64)`

## Decoder (`MsgPackReader`)

- `read_nil() -> Bool`, `read_bool() -> Maybe[Bool]`
- `read_u64() -> Maybe[U64]`, `read_i64() -> Maybe[I64]`
- `read_str() -> Maybe[Str]`
- `read_array_header() -> I64`, `read_map_header() -> I64`
- `position() -> I64`, `remaining() -> I64`

Returns `Maybe[T]` instead of `Outcome[T, E]` to avoid LL(1) parser
limitations with the `?` operator in if/else chains.

## v0.3.23 — Fix i128 Binary Operations in Codegen

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Fixes a codegen bug where all U128/I128 binary operations (`==`, `!=`, `<`,
`>`, `+`, `-`, `*`, `/`, `%`) emitted `i32` LLVM instructions instead of
`i128`. This caused K001 compilation failures for any code using 128-bit
integer arithmetic, including the new `U128::to_string()` and `std::msgpack`.

## Root Cause

`compiler/src/codegen/llvm/expr/binary_ops.cpp` line ~690 — the `int_type`
determination ladder had checks for `i1`, `i64`, `i16`, `i8` but **no check
for `i128`**. When both operands were `i128`, none of the conditions matched
and `int_type` defaulted to `"i32"`.

## Fix

Added `i128` check before the `i64` check:

```cpp
} else if (left_type == "i128" || right_type == "i128") {
    int_type = "i128";
} else if (left_type == "i64" || right_type == "i64") {
```

## Impact

- `U128::to_string()` and `I128::to_string()` now work at runtime
- `std::msgpack` writer/reader tests pass (2/2)
- Compiler suite: 265/266 (only pre-existing let_patterns X002)
- Any TML code using U128/I128 arithmetic is now correct

## v0.3.25

**Date:** 2026-04-15

## feat(std): BTreeMap for-in iteration (phase0p)

`BTreeMapIter[K,V]` now implements `Iterator[MapEntry[K,V]]`, enabling idiomatic
for-in loops over BTreeMap entries:

```tml
for entry in map.iter() {
    println(entry.key)
    println(entry.value)
}
```

### Changes
- Added `MapEntry[K,V]` type with `key` and `value` fields
- Implemented `Iterator` behavior on `BTreeMapIter[K,V]`
- Renamed cursor API `next()` to `advance()` to avoid conflict with `Iterator::next()`
- Fixed type checker generic substitution for `Iterator::Item` resolution
- Fixed codegen to mangle generic type args in for-in iterator dispatch
- Fixed codegen to request generic method instantiation for for-in loops
- Fixed Maybe payload extraction via GEP (avoids `[2 x i64]` vs `%struct` type mismatch)

## fix(codegen): remove 13 silent i32 type fallbacks (phase0x)

Removed all dangerous `= "i32"; // default/fallback` patterns across AST and MIR
codegen. When the compiler cannot resolve a type, it now uses the actual inferred
type from `last_expr_type_`, emits `unreachable`, or defaults to `i64` (TML's
native integer) — never silently falls back to `i32`.

### Files fixed
- `mir/instructions.cpp` — AwaitInst
- `method_generic.cpp` — closure/func params, generic return
- `method_class.cpp` — class method return
- `binary.cpp` — deref assignment, array element
- `closure.cpp` — closure param
- `method_primitive_ext.cpp` — primitive ext arg
- `unary.cpp` — deref operation
- `call_indirect.cpp` — indirect call return
- `method_dyn.cpp` — dyn trait method return
- `method_impl_module.cpp` — impl module arg
- `intrinsics_extended.cpp` — checked arithmetic
- `mem.cpp` — mem::zeroed

## build: test executables moved to `build/tests/`

`tml_tests` and `serial_reader_test` now output to `build/debug/tests/` instead of
`build/debug/bin/`. They only build with `--tests` flag.

## docs: Zig 0.16 incompatibility

Zig 0.16 breaks the build due to UCRT linking changes and `/failifmismatch`
RuntimeLibrary errors with pre-built LLVM static libs. README updated to require
Zig 0.14–0.15.x (pinned to 0.15.2).
