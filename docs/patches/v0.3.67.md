# v0.3.67 — MCP tools route through the warm compile daemon (phase40a)

**Date:** 2026-07-17
**Phase:** phase40a (MCP daemon warm path) — F-016 / F-017
**Analysis:** `docs/analysis/tooling-performance/` (01, 03, 05)

## Summary

Every `mcp__tml__check`/`compile`/`build`/`emit-ir`/`emit-mir` call used to spawn
a fresh cold `tml.exe` subprocess (~450 ms for a trivial check). The warm compile
daemon (`tml daemon`) already answered cache-hits in single-digit milliseconds but
nothing in the MCP path opted into it. The MCP server now launches daemon-eligible
children with `TML_DAEMON=1` in a per-child environment block and auto-starts the
daemon (throttled, detached) when it is not running.

**Measured:** `check` on an unchanged file 452.8 ms → **6.6 ms** median at the CLI
level (69×), **26–31 ms** through the full MCP JSON-RPC stack. Gate < 50 ms: PASS.

## Changes

- `compiler/src/mcp/mcp_tools.cpp` — `execute_command(cmd, timeout, use_daemon)`;
  warm-daemon helpers: PID-file liveness probe (same CRC32C(cwd) key as
  `cmd_daemon.cpp`), throttled detached auto-start of `tml daemon start`, and a
  per-child ANSI environment block carrying `TML_DAEMON=1` (thread-safe — no
  process-wide `_putenv_s`). `check`/`compile`/`build` handlers opt in; `run`
  deliberately stays cold (program stdout would be lost in the daemon's NUL
  std handles); `test` is not a forwardable command.
- `compiler/src/mcp/mcp_tools_codegen.cpp` — `emit-ir`/`emit-mir` handlers opt in.
- `compiler/src/launcher/main_launcher.cpp` + `compiler/src/cli/commands/cmd_daemon.cpp`
  — the daemon's "compiler updated, restarting" staleness notice now makes the
  client fall through to direct compilation instead of surfacing a spurious exit-1.
- `compiler/src/cli/dispatcher.cpp` — daemon forwarding moved above the `check`
  handler; it previously sat after it, making daemon forwarding for `check`
  unreachable in the DLL dispatcher (masked in modular builds by the thin
  launcher's pre-DLL forward).

## Lifecycle safety

- `scripts/build.bat:192` kills all `tml.exe` (including the daemon, which runs as
  `tml.exe __daemon_server`) on every build — no locked DLLs, no stale daemon.
- Second net: the daemon self-checks `tml_compiler.dll` mtime per request and exits
  when stale; clients now fall through cleanly (see above).
- Daemon absent/killed at any point → correct-but-cold result + auto-restart on the
  next MCP call (fire-and-forget, 10 s spawn throttle).

## Tests

`compiler/tests/cli/daemon_warm_path.sh` — 13 checks: fallback when daemon absent,
warm/cold output parity, cache-hit latency, hard-kill mid-session fallback,
stale-DLL fall-through + daemon self-exit, MCP-server auto-start (drives
`tml_mcp.exe` over stdio JSON-RPC). 13/13 PASS; `mcp_timeout.sh` regression 2/2 PASS.

## Notes

- Live MCP sessions talk to the `tml_mcp.exe` that was running at connect time;
  reconnect MCP after a rebuild to get the new routing.
- Daemon cache-hits return recorded stdout/stderr; on-disk artifacts (`.ll`, `.mir`,
  exe) persist from the cache-miss run and are not re-produced on a hit.
