# v0.3.40 — phase24b: C17 type-system value-pass crash fixed

**Date**: 2026-05-01
**Branch**: `feat/self-hosting-compiler`
**Task**: `phase24b_cc-typedef-name-resolution` Phase 3

## Summary

Fixed the codegen-grade ownership bug that crashed `tml cc` on a C source
that uses a typedef'd name as a parameter type:

```c
typedef int int32_t;
int32_t add(int32_t a, int32_t b) { return a + b; }
```

Before this patch the second parameter (`int32_t b`) crashed inside
`compiler-tml/src/cc/types.tml::base_to_ctype` with an
ACCESS_VIOLATION on the `env.typedefs.get(name)` heap dereference.

## Root cause

`CTypeEnv` is a struct of four `HashMap` fields:

```tml
pub type CTypeEnv {
    target: CAbiTarget,
    typedefs: HashMap[Str, Heap[CType]],
    structs:  HashMap[Str, Heap[CAggregate]],
    unions:   HashMap[Str, Heap[CAggregate]],
    enums:    HashMap[Str, Heap[CEnumType]]
}
```

A `HashMap` is `{ buckets: ptr, len, cap }` — three fields where
`buckets` is a heap-allocated array.

`base_to_ctype(env: CTypeEnv, b: CBaseType)` and the other type-system
entry points in `types.tml` took `env` by value. On entry, the callee
gets a bitwise copy of the struct, so both copies' `typedefs.buckets`
pointers alias the same allocation. On exit, drop glue runs on the
callee's local `env`, calling `HashMap::drop` and `mem_free`-ing the
buckets — but the caller's `lw.env.typedefs.buckets` still points at
the freed memory. The second call into the type-system from the same
caller (`base_to_ctype` for the second function parameter) re-enters
the freed bucket array and crashes on `Heap.get()`.

The same shape exists for `structs`, `unions`, `enums`, and any other
HashMap-bearing struct passed by value through TML's current ABI.

## Fix

Switched every type-system entry point to take `env: ref CTypeEnv`,
eliminating the copy + drop. Affected functions:

- `base_to_ctype`
- `apply_declarator`
- `resolve_type_name`
- `sizeof_type` / `sizeof_heap`
- `alignof_type` / `alignof_heap`
- `size_for_kind`
- `layout_struct` / `layout_union`
- `ptr_add_scale`

Internal forwards within `types.tml` pass `ref env`. External callers
in `compiler-tml/src/cc/lower.tml` pass `ref lw.env` (TML allows `ref`
on a struct field access).

## Why `ref` and not a codegen fix

The proposal listed three candidates:

1. **`env: ref CTypeEnv` everywhere** — TML-side, surgical, no
   language change. Selected.
2. **Codegen elides field-level drops on a value-passed local when
   the field is a single pointer** — would also fix the bug class
   project-wide, but requires careful invariants in the C++ codegen
   (`compiler/src/codegen/llvm/decl/func.cpp`,
   `compiler/src/codegen/llvm/expr/return_stmt.cpp`) and a deeper
   audit of every existing pass-by-value site that depends on drop
   semantics. Larger blast radius; deferred.
3. **Explicit borrow semantics for struct value parameters** —
   language change; out of scope.

Option (1) is the minimum-code fix that follows established TML
patterns (`ref Buffer`, `ref List[I64]`, `ref FieldDescriptor`). Other
HashMap-bearing structs in the codebase (e.g. `CLower`, `CParser`,
`MirModule`) ship a similar pattern but pass `lw: CLower` etc. through
hundreds of call sites — those have been getting away with the same
bug class because their methods mutate via the shared backing store
in ways that don't trigger drop glue, but they are not safe in
principle. A future codegen patch (option 2) is the long-term fix;
this one closes the immediate crash that blocks `tml cc`.
