# v0.3.46 — `List[Str]::push` K001 codegen fix (phase0y)

**Released**: 2026-05-02
**Branch**: feat/self-hosting-compiler
**Task**: `.rulebook/tasks/phase0y_list-str-push-i64-ptr-k001/`

## Summary

Fixes two interacting bugs in the AST-legacy codegen path for impl-method
calls that crashed `tml build compiler-tml/src/main_frontend.tml` (and 11
self-host lexer/parser tests) with:

```
[K001] Failed to parse LLVM IR: ir:NNNN: error: '%tN' defined with type
'i64' but expected 'ptr'
  %tM = call {} @tml_N3std11collections4list9List__Str9push__I64E(
                       ptr %tR, ptr %tV)
```

Root cause was concentrated in
`compiler/src/codegen/llvm/expr/method_impl.cpp::try_gen_impl_method_call`.

## Minimal repro

`compiler-tml/src/intern.tml::InternTable::intern` writes:

```tml
this.strings.push(s as I64)   // strings: List[Str]
```

Reduced to:

```tml
use std::collections::list::List
func main() -> I32 {
    var l: List[Str] = List[Str]::new(0 as I64)
    let s: Str = "hello"
    l.push(s as I64)
    return 0
}
```

Both the trivial form `l.push("hello")` and the cast form
`l.push(s as I64)` had to round-trip through the same call-site codegen
to expose both bugs.

## Bug 1 — impl-level `T` re-inferred as a method-level generic

`try_gen_impl_method_call` ran a "method-level type-param inference"
branch when `call.type_args.empty() && !func_sig->type_params.empty()`.
The branch set:

```cpp
size_t impl_param_count = named.type_args.size();
if (impl_param_count >= func_sig->type_params.size()) {
    impl_param_count = 0;   // ← incorrect for impl-method shape
}
```

The intent was to handle trait-method registrations
(`env_module_load_decls.cpp:904-909`) where `func_sig->type_params`
contains ONLY the method's own generics — the impl-level params have
already been substituted away at registration time. For `fold[B]` on
`ListIter[I64]`, `func_sig->type_params=["B"]` and
`named.type_args=["I64"]`; resetting `impl_param_count=0` correctly
inferred `B`.

But impl-method registrations
(`env_module_load_decls.cpp:466-475`) put impl-level generics at the
HEAD of `type_params`, then append the method's own generics. For
`impl[T] List[T] { func push(this, value: T) }`,
`func_sig->type_params=["T"]` is the impl-level T, and
`named.type_args=["Str"]` already binds it. The legacy heuristic
incorrectly reset `impl_param_count=0` and re-inferred `T` from the
call argument — so when `s as I64` produced an `I64` arg, the codegen
minted `push__I64` as the method-level type suffix, generating a
nonsensical specialization name
`tml_N3std11collections4list9List__Str9push__I64E` whose declared
signature `(ptr, ptr)` did not match the call site's `(ptr, i64)`.

`FuncSig::impl_self_type_args` is set ONLY for impl-method
registrations. We use its size to authoritatively count impl-level
params at the head of `type_params`, falling back to the legacy
heuristic only when the field is unset (trait methods, default
behavior methods loaded from binary cache).

## Bug 2 — missing int↔ptr argument coercion

Once Bug 1 was fixed, the call site emitted the correct callee name
`tml_N3std11collections4list9List__Str4pushE` but still passed `i64`
for the `ptr` parameter. The argument coercion block in
`method_impl.cpp` had branches for int→int (sext/trunc) and
ptr→`{ ptr, ptr }` fat-pointer wrapping, but no fallback for the
straight int↔ptr case that user-written `as I64` on a `Str` produces.

Added two coercions in the same `actual_type != expected_type` block:

```cpp
// int -> ptr (e.g., user wrote `s as I64`)
else if (is_int_actual && expected_type == "ptr") {
    emit_line("  " + fresh + " = inttoptr " + actual_type + " " + val + " to ptr");
}
// ptr -> int (mirror)
else if (actual_type == "ptr" && is_int_expected) {
    emit_line("  " + fresh + " = ptrtoint ptr " + val + " to " + expected_type);
}
```

Mirrors the int↔ptr fallback already present in the cast lowering
path. No effect on calls where the user did not write a numeric cast.

## Why the trivial repro built clean before the fix

`l.push("hello")` worked because `infer_expr_type` on a string literal
returned `Str`, which matched the impl-level T and produced
`method_type_suffix = "Str"`. The codegen then went looking for
`push__Str`, didn't find it (because impl emits `push` under the
unsuffixed name), and silently fell back to the unsuffixed name via
`mangle_impl_method`. So the call appeared to work despite the inference
being structurally wrong.

`l.push(s as I64)` made the inference produce `__I64` and the
mangled-name fallback failed because `push` was emitted as `push`
(unsuffixed), but the Itanium-encoder packed the suffix into the length
prefix of the method segment (`9push__I64` instead of `4push`),
generating a callable that no definition matched. The verifier caught
the resulting i64-vs-ptr mismatch at the call site.
