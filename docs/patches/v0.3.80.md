# v0.3.80 — phase26c: phase24 band-aid revert + structural clone-glue for `ptr_read_clone` (ERA 0, Phase B gate)

**Date:** 2026-07-19
**Task:** `phase26c_memmodel-bandaid-revert`
**Branch:** `fix/era0-stabilization`

The proof that phase26b actually fixed the memory model is that the phase24
workarounds can be deleted and everything still passes. This patch deletes
them on the non-frozen surface — and, in doing so, exposed and fixed one
remaining soundness hole in the fix mechanism itself.

## 1. Band-aid inventory (item 1.1)

- The headline phase24 band-aids (`into_raw()`/`from_raw()` drop-suppression
  chains, `declarator_name_value_leak`) were **already deleted in phase24g
  (v0.3.45)** — only comments referencing them remained.
- The remaining live in-scope band-aids were all API-surface: `Shared.get`
  was still the OLD unsound bitwise copy carrying a 20-line hazard docstring
  (phase24k), `Shared.get_ref` sat on the `ptr_as_ref` intrinsic (documented
  in sync.tml as mis-typing its return as `i32`), and historical
  F-016/phase24/phase26b narrative comments littered `sync.tml`, `heap.tml`,
  `hashmap.tml`, `list.tml`.
- C++ side: the only phase24 artifacts are the `ptr_read_clone` intrinsic +
  its LLVM/MIR codegen — that is the phase26b **fix mechanism**, kept.
- Frozen `compiler-tml/src/cc/` record (do-not-touch until phases 30–33):
  180 `.duplicate()` partial-move calls, 10 manual `impl Duplicate`, the
  `CollectedArgs` flat-list dodge, 2 `get_clone` call sites.

## 2. API decision + revert (items 1.2/1.3)

- **`Shared.get` folded to sound semantics**: body is now the exact
  `Sync.get` pattern — `ptr_read_clone[T]` on the field-0 pointer. Nested
  refcounted handles in the returned copy carry fresh refcounts; plain load
  for primitive `T`. The last unsound bitwise reader in the alloc API is gone.
- **`Shared.get_ref` re-based** from `ptr_as_ref[T]` (mis-typed return) onto
  the `ref (*this.ptr).value` borrow pattern used by `Sync.get_ref`.
- **`get_clone`/`get_ref` KEPT** as documented API (`get_clone` is explicit
  deep-clone and is called by frozen compiler-tml; `get_ref` is the zero-copy
  path). **`ptr_read_clone` intrinsic KEPT** — canonical mechanism, guarded
  by `compiler/tests/compiler/get_deep_clone.test.tml`.
- **All hazard docstrings describing the dead bitwise-alias bug class
  removed** from `Shared`/`Sync`/`Heap`; historical narrative comments in
  `hashmap.tml`/`list.tml` shrunk to one-line rationale.

## 3. Codegen fix: structural clone-glue synthesis (found by the new gate tests)

New regression file `lib/core/tests/alloc/shared_get_sound.test.tml`
(bump-on-get / restore-on-drop / zero-copy `get_ref`) exposed that
`ptr_read_clone[T]` was **silently bitwise** for a plain user struct with a
`Shared` field but NO explicit/derived `Duplicate` impl
(`type BoxedCounter { inner: Shared[I64], tag: I64 }`) — i.e. the phase24
double-free shape survived for underived user aggregates. Two symmetric
halves, both fixed:

- `intrinsics.cpp`: auto-clone detection gated solely on `has_duplicate_impl`
  → now clones when `env_.type_needs_drop(T) || struct_has_droppable_field(T)`
  (the same predicate drop-glue uses). New
  `LLVMIRGen::gen_structural_duplicate()` (`derive/duplicate.cpp`)
  synthesizes field-wise clone glue for needs-drop aggregates lacking an
  explicit impl — deep-clone droppable fields, bitwise for genuine PODs;
  idempotent, recursion-safe. Handle-free PODs keep the bitwise fast path.
- `llvm_ir_gen_stmt_let.cpp`: `suppress_field_drops` only registered a drop
  for a method-initialized `let` when the type had a DIRECT Drop impl —
  field-level-only droppables (the same `BoxedCounter` shape) were never
  dropped. Now registered.

**Debugging correction of record:** the bug initially looked
composition-sensitive (standalone pass / suite fail). The per-module IR is
byte-identical — the codegen was uniformly broken; the standalone "pass" was
a test-harness FALSE-PASS (the standalone dispatcher emits `test_pass` even
when the body panics). Filed as `phase44a_test-dispatcher-false-pass`.
