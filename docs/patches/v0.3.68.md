## Summary

The compiler everyone (and every agent) used daily was the unoptimized `-O0`
debug build (`scripts/build.bat` defaults `BUILD_TYPE=debug`). phase40b ships and
validates the **release** (`-O3 -DNDEBUG`) build as a first-class daily driver:

- **Audit:** under the Zig CC toolchain (ADR-007) the Release config applies
  `-O3 -DNDEBUG` to **all 40 CMake targets** — verified per-object in the
  generated `build.ninja` (0 unoptimized objects). No CMakeLists fix was needed;
  F-001 was purely the debug *default build type*.
- **Build:** `scripts\build.bat release` builds clean — 507/507 ninja steps,
  0 release-only compile/link errors → `build/release/bin/tml.exe` + all plugin
  DLLs (`tml_compiler.dll` 77.2 MB, `tml_codegen_x86.dll` 52.0 MB).
- **Measured (cold path, no daemon, medians, n=7 / n=3):**

  | Workload | debug | release | speedup |
  |---|---|---|---|
  | `tml check` trivial file | 396.3 ms | 213.0 ms | **1.86×** |
  | `tml check` `lib/core/src/task.tml` (714 lines) | 5502.1 ms | 2702.6 ms | **2.04×** |
  | 49-file suite compile+run (core/hash + compiler/borrow + std/json) | 66.60 s | 31.52 s | **2.11×** |

- **Sanity:** 49/49 tests pass identically on both binaries (3 runs each);
  `check` diagnostics byte-identical; the working tree's pre-existing K001
  failures reproduce byte-identically (same generated-IR line:column) under both
  binaries — deterministic codegen, no optimization-induced miscompile.

## MCP/daemon wiring — documented, deliberately NOT flipped

MCP/daemon stay on the debug binary. Reasons (full write-up in
`docs/analysis/tooling-performance/02-build-performance.md`):

1. Binary selection is a hardcoded candidate order in `get_tml_executable()`
   (`compiler/src/mcp/mcp_tools.cpp:752`) — switching is a C++ change, not a
   safe/reversible config flip.
2. The test result/EXE cache is shared and debug-anchored
   (`build/debug/cache/tests.json`), keyed on the *running* binary's
   `tml_compiler.dll` fingerprint — every debug↔release alternation invalidates
   ALL cached test EXEs (~837 MB of recompiles thrash for concurrent sessions).
3. The daily C++ rebuild loop refreshes debug only; a release-wired MCP would
   silently serve stale compiler code after every codegen fix.
4. phase40a's warm daemon already answers unchanged-input MCP calls in ~7 ms —
   release only helps cache-miss compiles.

The exact switch procedure (accepting those caveats) is documented in the same
file.

## Daily-driver guidance

- Use `build/release/bin/tml.exe` directly for compile-heavy CLI work (long
  suite runs, batch check/build, benchmarks, migration sweeps): ~2× wall-clock.
- Keep `build/debug/bin/tml.exe` for C++ compiler debugging and for everything
  routed through MCP/daemon.
- Refresh release after C++ changes with `cmd //c "scripts\\build.bat release"`
  (fast with a warm zig cc cache; the release tree is fully additive).
