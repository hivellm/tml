# v0.3.7 — List `@inline` / LLVM `alwaysinline` support (phase0e)

## Summary

`@inline` (and `@always_inline`) decorators on TML functions now emit
`alwaysinline` in the generated LLVM IR, causing the LLVM optimizer to
unconditionally inline the call site. Previously the attribute was parsed
and stored in MIR but never propagated to the LLVM backend.

## Changes

### `lib/std/src/collections/list.tml`

Added `@inline` to the five hot `List[T]` methods:
- `push(this, value: T)`
- `pop(this) -> T`
- `get(this, index: I64) -> T`
- `set(this, index: I64, value: T)`
- `len(this) -> I64`

### `compiler/src/codegen/llvm/decl/impl.cpp`

- `gen_impl_method` — scans `method.decorators` for `"inline"` /
  `"always_inline"` / `"noinline"` / `"never_inline"` and appends
  `alwaysinline` or `noinline` to the emitted `define` signature.
- `gen_impl_method_instantiation` — same for generic method
  instantiations (the path taken by `List[I64]`, `List[I32]`, etc.).

### `compiler/src/codegen/llvm/decl/func.cpp`

- Regular function path and generic function instantiation path:
  same decorator → LLVM attribute propagation.

### `compiler/src/codegen/mir_codegen.cpp`

- MIR codegen path: `func.attributes` checked for `"inline"` and
  `"noinline"` before the heuristic (name-based) logic, so explicit
  annotations take priority over heuristics.

## Benchmark Results (release mode, 10M iterations)

| Benchmark | TML | Rust | Ratio |
|---|---|---|---|
| Push (grow) | 300 M ops/s (3 ns) | 282 M ops/s | 1.06× (TML ahead) |
| Push (reserved) | 914 M ops/s (1 ns) | 687 M ops/s | **1.33× (TML ahead)** |
| Random Access | 2.9 B ops/s (<1 ns) | 1.4 B ops/s | **2.02× (TML ahead)** |
| Pop | 3.1 B ops/s (<1 ns) | 579 M ops/s | 5.3× (TML ahead) |
| Set | 2.9 B ops/s (<1 ns) | 3.3 B ops/s | 0.88× (parity) |

Gate results:
- List Push (reserved) < 3 ns/op: **1 ns ✓**
- List Access < 2 ns/op: **<1 ns ✓**
- TML/Rust ratio < 2.5×: **all pass ✓**
