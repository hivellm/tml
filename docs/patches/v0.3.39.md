# v0.3.39 — C17 frontend parser unblocked (2026-05-01)

## Highlights

`cp_parse_translation_unit` on `int x;` finally exits 0. Two compounding
bugs were stacked on top of each other; both are fixed in this release.
`tml cc <file>.c --emit=ast` now drives the full preprocess → tokenize →
parse pipeline end-to-end on a real C source. Phase24 Phase 4
(self-compile of `essential.c` / `mem.c` via `tml cc`) is unblocked.

## Bug 1 — Dangling-Str leaks in the C17 parser

**Symptom**: random garbage in declarator names, sometimes a clean
`'x'`, sometimes the substring of a previous instrumentation message.

**Root cause**: `compiler-tml/src/cc/parser.tml` had five raw
`parser.tokens.get(p)` reads inside loop bodies (lines 287, 478, 536,
677, 960). `List.get` returns a bitwise copy via `ptr_read[T]`, which
for a `CToken` means the returned value's `Str` fields share heap
pointers with the list slot. When the local `tok` fell out of scope at
end of iteration, its drop glue called `tml_str_free` on those shared
pointers, corrupting the list for subsequent reads. A second class of
leak: at every site where `tok.text` or `tok.file` flowed into a
struct/enum payload that outlived `tok`, the bitwise-copy semantics
made the captured string dangling once `tok` dropped.

**Fix**: routed every token read through `cp_peek` (which already
`.duplicate()`s Str fields via `cp_dup_token`); added explicit
`.duplicate()` at every escape site (~25 sites) — `c_parse_err.file`,
`cp_expect_ident.name`, `CBaseType::Typedef`, `CExpr::Ident`,
`CDeclarator::Ident`, all 10 `start_tok.file` captures across the
struct/union/enum/func/typedef/var decl emitters, the label and
`_Static_assert` paths, and `declarator_name` itself (so
HashMap/struct captures of the returned name don't dangle either).

Shipped in commit `7e70a7bc7` earlier in the session.

## Bug 2 — ABI mismatch in static method dispatch

**Symptom**: `cp_parse_translation_unit(parser, "t.c")` segfaulted at
`Heap[CDecl]::new(CDecl::Var(vd))` even with literal Strs — the
generated LLVM IR had a calling-convention mismatch:

```llvm
define internal %struct.Heap__MinDecl @...3newE(ptr %value) ...
  %t186 = load %struct.MinDecl, ptr %value     ; expects pointer
...
  %t20 = call ...3newE(%struct.MinDecl %t14)    ; passes value
```

`%t14` is the `CDecl` struct value; `%value` is reinterpreted as a
pointer (taking the first 8 bytes = i32 discriminant + padding = 0);
`load from null` → ACCESS_VIOLATION at 0x0.

**Root cause**:
`compiler/src/codegen/llvm/decl/impl.cpp:392-395` lowers the first
non-self struct/enum param of a non-instance method to `(ptr %value)`
in the LLVM definition. The matching call-side fixup at
`compiler/src/codegen/llvm/expr/method_static_dispatch.cpp:1006-1020`
looked up `functions_["<mangled_type_name>_<method>"]` to decide
whether to alloca+store+pass-ptr.

For generic instantiations like `Heap[CDecl]::new`, the FuncInfo is
registered under `Heap__CDecl_new`, but the instantiation only runs as
part of a subsequent codegen pass after `pending_impl_method_instantiations_`
is drained. At arg-processing time the FuncInfo lookup returned
`functions_.end()`, the conversion was bypassed, and the struct was
emitted as a value argument to a pointer-expecting callee.

The synthetic regression tests for bugs #7/#8/#9 missed this case
because their `BigStruct` / `Inner` / `Outer` shapes differ from the
specific `{ Str, InnerEnum(Str)|B, Str, I64 }` shape that triggers
the crash; bisected through 19 minimal variants (steps A–S in
`compiler/tests/compiler/heap_decl_var_repro.test.tml` history) to
isolate the trigger.

**Fix**: added a fallback in `method_static_dispatch.cpp:1006-1029` —
when the FuncInfo lookup misses AND `i == 0` AND the resolved arg type
starts with `%struct.` or `%enum.`, mirror the `impl.cpp:392-395` rule
unconditionally (alloca + store + pass `ptr`). Scoped to the
`func_sig` branch only; the other two branches at lines 1081+ and
1162+ already handle their own cases through `pending_generic_impls_`
lookups.
