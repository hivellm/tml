## v0.3.0 — Language Ergonomics Sprint

**Date:** 2026-04-11

## Summary

Major ergonomics release implementing 9 language improvements identified from a comprehensive codebase analysis (15 findings across compiler-tml, core, and std). All changes are backwards-compatible. Specs and grammar updated to match.

## Language Features

### For-in Range Loops (phase30a)
`for` loops with `to` (exclusive) and `through` (inclusive) ranges now work in the MIR codegen path:
```tml
for i in 0 to 10 {         // 0, 1, ..., 9
    process(i)
}
for i in 1 through 5 {     // 1, 2, 3, 4, 5
    sum = sum + i
}
```
- Desugars to counter loop: alloca + header (load+cmp) + body + increment + backedge
- SSA phi nodes for mutable outer variables (same pattern as while loops)
- Extracts start/end directly from Range struct expression to avoid type mangling

### Pattern Guards (phase30b)
Pattern guards with `if` in `when` arms were already implemented but undocumented. Now verified and tested:
```tml
when value {
    Just(x) if x > 0 => handle_positive(x),
    Just(x) => handle_nonpositive(x),
    Nothing => handle_missing(),
}
```

### Struct Update Syntax (phase30c)
`..base` in struct literals copies unspecified fields from the base expression:
```tml
let p2: Point = Point { x: 999, ..p1 }
// p2.x = 999, p2.y = p1.y, p2.z = p1.z
```
- MIR path: added `base` and `from_base` fields to `StructInitInst`, emitter extracts fields with `extractvalue`
- Legacy AST path: field-by-field GEP copy for non-specified fields
- DCE updated to track `StructInitInst.base` value references

### Struct Destructuring in Let (phase30i)
Struct pattern destructuring in `let` bindings:
```tml
let Pair { first: a, second: b } = get_pair()
// a = pair.first, b = pair.second
```
- Added `StructPattern` handler in `gen_let_stmt` (legacy AST codegen)
- Emits alloca + GEP + load for each field binding
- Bool i8→i1 trunc included for Bool struct fields

### Bool Struct Field Layout Fix (phase30f)
Bool (`i1`) in struct fields caused LLVM alignment bugs. Now promoted to `i8` in struct contexts:
- **Struct declaration**: `i1` → `i8` in all field registration paths (5 codegen paths)
- **Field load**: `load i8` then `trunc i8 → i1`
- **Field store**: `zext i1 → i8` then `store i8`
- Registers and function parameters remain `i1` (no change)
- Fixes `Cell[Bool]` generic instantiation (binary.cpp field assign path)

### Operator Overloading (phase30d)
Binary operators on user-defined structs now dispatch to behavior methods:
```tml
use core::ops::Add

type Vec2 { x: I32, y: I32 }

impl Add[Vec2] for Vec2 {
    pub func add(this, rhs: Vec2) -> Vec2 {
        return Vec2 { x: this.x + rhs.x, y: this.y + rhs.y }
    }
}

let c = a + b  // calls Vec2::add(a, b)
```
- THIR lowering resolves non-primitive operators to behavior method calls via trait solver
- MIR builder emits `CallInst` with mangled function name (`Vec2__add`)
- AST legacy codegen: added struct-aware dispatch in `binary_ops.cpp` (fixes K001 GEP bug)
- Primitives (I32, I64, F64) still use built-in LLVM arithmetic — no behavior dispatch overhead
- Supports: `+`, `-`, `*`, `/`, `%`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `&`, `|`, `^`, `<<`, `>>`

### Directives: @repr, @auto, @packed (phase30e)

**@repr(U8/U16/I32/I64)** on enums — assigns sequential discriminants with a specific integer type:
```tml
@repr(U8)
enum Color { Red, Green, Blue }
// Red=0, Green=1, Blue=2; `color as I32` extracts discriminant
```

**@auto(behaviors...)** — alias for `@derive` with lowercase name mapping:
```tml
@auto(duplicate, equal, debug)  // equivalent to @derive(Duplicate, PartialEq, Debug)
type Point { x: I32, y: I32 }
```

**@packed** — emits struct with LLVM packed layout `<{ ... }>` (no inter-field padding):
```tml
@packed
type Header { magic: I32, version: I8, flags: I32 }  // 9 bytes, not 12
```

### Closure Type Inference (phase30g)
Closure parameters infer types from the expected function signature (bidirectional inference):
```tml
func apply(f: func(I32) -> I32, x: I32) -> I32 { return f(x) }

let r = apply(do(x) { x + 10 }, 5)  // x inferred as I32, return inferred as I32
```
- Parser already supported optional `: Type` on closure params
- Type checker creates fresh type vars, unifies with expected `func(T) -> U` signature
- Implicit return: single-expression closure body used as return value
- Inferred types stored in AST for HIR builder and legacy codegen

### Behavior Aliases (phase30h)
Named combinations of trait bounds:
```tml
behavior Describable = Printable
behavior Numeric = Add[Self] + Sub[Self] + Mul[Self]

func sum[T: Numeric](a: T, b: T) -> T { return a + b }
```
- New `BehaviorAliasDecl` AST node parsed via `behavior Name = Bound1 + Bound2`
- LL(1) safe: after `behavior Ident`, peek `=` → alias; peek `{` → full definition
- Type checker registers alias → constituent bounds mapping, expands at usage sites

## v0.3.2 — Codegen Bug Fixes + Runtime Stability + `tml cv` In-Process

**Date**: 2026-04-12

## Highlights

  share the counter across value-copied instances; fixes STACK_BUFFER_OVERRUN in unify tests
- **`tml cv` in-process**: replaced `_popen("tml.exe check ...")` subprocess with an
  inline lexer→parser→type-checker call — fixes 0/91 false failures on Windows
- **27/28 compiler-tml tests pass** (was 20/27 before this release)

## Fixed

### Codegen (AST Path)

- **K001 enum discriminant**: enums were not registered in `struct_fields_` so
  `cast.cpp` could not find field-0 type when truncating i64→i32 in enum init.
  Fixed at 3 sites: `emit_enum_def()` (×2 in `enum.cpp`) and `llvm_types.cpp`.
- **Type alias resolution**: non-generic type aliases (e.g. `ValueId = I64`) were
  not resolved before IR emission — now looked up in the alias map in `llvm_types.cpp`.
- **Boolean coercion**: logical `and`/`or` operands now coerce i64→i1 before
  `llvm::IRBuilder::CreateAnd/Or` in `binary_ops.cpp`.

### Runtime (compiler-tml)

- **`InferCtx` shared counter**: `next_var_id: I64` was a scalar field — each copy
  of `InferCtx` (value type) had its own counter. Both callee increments were lost on
  return, so `fresh_var()` always returned `TypeVar(0)` in the caller. Fixed by
  changing to `var_counter: List[I64]` (one-element list); `List` holds a single
  `handle: *Unit` pointer, so all copies share the same heap-allocated element.
- **`unify_resolved` Primitive mismatch**: the Primitive→Primitive arm returned
  `false` on kind mismatch without pushing a `TypeError`. Downstream `assert(has_errors(ctx))`
  then failed with a noreturn assert handler, corrupting RBP to 0xAB (Windows debug heap fill)
  and causing ACCESS_VIOLATION at 0x8. Fixed by adding `ctx.errors.push(...)` before returning.

### `tml cv` Coverage Command

- **In-process type-check**: `type_check_file()` previously spawned `_popen("tml.exe check ...")`
  which launched `tml.exe` as a Windows cmd.exe subprocess. The compiler DLLs are not in
  the Windows system PATH (only in the Git Bash PATH), so all 91 files failed with exit
  code 2 (DLL not found). Replaced with a direct inline lexer→parser→type-checker call
  inside the same process. `preload_all_meta_caches()` is now called once before the batch.
  Result: **84/91 sources pass** (7 pre-existing type-check failures unrelated to K001).

## v0.3.4 — 2026-04-14

## Fixed

### K001: bool/i32 mismatch in `icmp eq`/`ne` comparison emission (AST codegen)

**Root cause**: In `binary_ops.cpp`, when one operand of a `==` or `!=` comparison had
type `i1` (bool) and the other had a wider integer type (e.g. `i32`), the codegen emitted
`icmp eq i1 %wider_val, 1` — using the narrower `i1` instruction type for a register that
was actually `i32`. LLVM's IR verifier rejected this as an invalid instruction.

**Trigger**: The `Just(expr == 1)` pattern, where `expr` has type `I32` and the literal
`1` was typed as `i1` due to enum constructor context setting `expected_literal_type_`.
`is_bool` became `true` (because right operand was `i1`), setting `int_type = "i1"`, but
the left operand (`result: I32`) was loaded as `i32`, causing a type mismatch.

**Fix**: In `BinaryOp::Eq` and `BinaryOp::Ne` in `compiler/src/codegen/llvm/expr/binary_ops.cpp`,
when `int_type == "i1"` and one operand is a wider integer type, insert a `zext i1 %v to <T>`
instruction to widen the `i1` operand to the wider type before the `icmp`. This preserves
exact equality semantics (`zext i1 1 to i32 = 1`).

**Confirmed fix**: `std::json::Json::as_bool` and `std::json::Json::is_bool` now emit correct
`icmp eq i32` IR. `benchmarks/profile_tml/json_bench.tml --stage=parser:cpp` compiles and
runs successfully (exit 0).

**No regressions**: core 50/50, std 10/10, compiler 224/224.

## Files changed

- `compiler/src/codegen/llvm/expr/binary_ops.cpp` — zext widening for `Eq`/`Ne` mixed i1/wider-int
- `docs/patches/v0.3.4.md` — this file
- `CHANGELOG.md` — v0.3.4 entry
- `VERSION` — bumped to 0.3.4

## v0.3.6 Patch Notes

**Date**: 2026-04-14
**Branch**: feat/self-hosting-compiler

## Performance — `switch` optimization for `when` expressions (phase0d)

### Summary

Integer `when` expressions with 4+ literal arms now emit a single LLVM `switch`
instruction instead of a cascading `icmp eq` + conditional branch chain.

### Benchmark results

| Benchmark | Before | After | Rust |
|-----------|--------|-------|------|
| When Dense (10 cases) | ~9.5 ns/op (icmp chain) | <1.5 ns/op (switch) | <1.5 ns/op |
| When Sparse (10 cases) | ~9.5 ns/op (icmp chain) | <1.5 ns/op (switch+btree) | <1.5 ns/op |

TML/Rust ratio: 1:1 (parity achieved).

### Technical details

**File**: `compiler/src/codegen/llvm/control/when.cpp`, `gen_when()`

**Eligibility criteria** (all must hold):
- Scrutinee type is an integer (`i1`, `i8`, `i16`, `i32`, `i64`)
- At least 4 arms have integer or bool literal patterns (`kMinSwitchArms = 4`)
- No arm has a guard condition
- No `OrPattern` arms

**Generated IR** (before):
```llvm
%t1 = icmp eq i64 %x, 0
br i1 %t1, label %when_arm0, label %when_next0
when_next0:
%t2 = icmp eq i64 %x, 1
br i1 %t2, label %when_arm1, label %when_next1
; ... 8 more comparisons
```

**Generated IR** (after):
```llvm
switch i64 %x, label %when_end [
  i64 0, label %when_arm0
  i64 1, label %when_arm1
  ; ... 9 more entries
]
```

LLVM's `switch` lowering selects jump tables for dense ranges and binary search
trees for sparse ranges — both are significantly faster than linear icmp chains.

### Regression test

`compiler/tests/compiler/when_switch_dense.test.tml` — 6 tests covering dense,
sparse, minimal (4 arms), bool scrutinee, default arm, and wildcard-as-default.

### No regressions

- Core test suite: 769/808 pass (39 pre-existing failures unchanged)
- Compiler test suite: 286/290 pass (4 pre-existing K001/method failures unchanged)
- Switch path gated on `is_int_scrutinee` — enum/string/struct `when` unaffected

## v0.3.8 — Boolean Short-Circuit Fix (phase0f)

**Date**: 2026-04-14  
**Branch**: feat/self-hosting-compiler

## Summary

`and` and `or` now correctly implement short-circuit evaluation. Previously, both operands were always evaluated eagerly because the operators fell through to `gen_binary_ops` which already had both SSA values computed. This release adds a 2-block phi layout that skips RHS evaluation when the LHS determines the result.

## Changes

### compiler/src/codegen/llvm/expr/binary.cpp

Added short-circuit block layout before delegating to `gen_binary_ops`:

- **`a and b`**: if `a` is false, branch directly to merge block; `b` is never evaluated.
- **`a or b`**: if `a` is true, branch directly to merge block; `b` is never evaluated.

The IR layout is:
```
and.entry:
  br i1 %lhs, label %and.rhs, label %and.merge
and.rhs:
  <evaluate b>
  br label %and.merge
and.merge:
  %result = phi i1 [ false, %and.entry ], [ %rhs, %and.rhs ]
```

**Bug fixed**: `current_block_` is a member variable that persists across function codegen boundaries. If the previous function ended with a `when_end` block, `current_block_` would still hold `"when_end784"` when the next function started. Using `current_block_` as the phi predecessor would reference a block from a different function — LLVM verification error `use of undefined value '%when_end784'`.

**Fix**: emit a fresh `and.entry`/`or.entry` block label via `br label %and.entry` + `and.entry:` before saving the phi predecessor. This guarantees the predecessor is always within the current function's scope.

LLVM's optimizer folds the 2-block phi back to a single `and i1` / `or i1` at O2 when both operands are pure (no side effects), so release-mode performance is identical to the eager form.

## v0.3.9 — Bounds-Check Elimination for for-in Loops (phase0g)

**Date:** 2026-04-14  
**Branch:** feat/self-hosting-compiler

---

## Summary

For `for i in 0 to n { ... }` loops, the compiler now emits `llvm.assume(i ult n)`
at the start of every loop body iteration. This informs LLVM's optimizer that the
loop variable is provably within `[0, n)`, enabling:

- **LICM (Loop-Invariant Code Motion)**: `stride` and `data_addr` header loads inside
  `List.get(i)` are hoisted out of the loop since LLVM can now verify they're
  invariant and the access is safe.
- **Auto-vectorization**: LLVM's vectorizer can safely widen the loop because it knows
  the index is in-bounds.
- **Elimination of redundant safety checks**: Any bounds-check-like branches added in
  the future are eliminated for the for-in pattern.

---

## Changes

### `compiler/src/codegen/llvm/control/loop.cpp`

`gen_for()`: After entering the loop body block for a 0-based range, emits:

```llvm
%__i = load <type>, ptr %var_alloca
%__cond = icmp ult <type> %__i, %range_end
call void @llvm.assume(i1 %__cond)
```

Applied only when:
- `range_start == "0"` (literal zero start — most common for list iteration)  
- `range_type != "i1"` (not a boolean edge case)

Does **not** affect semantics — `llvm.assume` is a pure optimizer hint with no
observable side effects.
