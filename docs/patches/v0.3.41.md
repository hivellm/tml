# v0.3.41 — phase24c: C17 typedef-as-func-param crash fixed

**Date**: 2026-05-01
**Branch**: `feat/self-hosting-compiler`
**Task**: `phase24c_cc-driver-runtime-link` (renamed scope: codegen
return-path bug → root cause was Heap-borrow-drop double-free)

## Summary

`tml cc` on a C source using a typedef'd type as a function parameter
no longer crashes:

```c
typedef int int32_t;
int32_t add(int32_t a, int32_t b) { return a + b; }
```

Pre-fix: `cc_driver` exited 127 silently on the second `base_to_ctype`
call (param 0 in `lower_func_decl`'s parameter loop).
Post-fix: `cc_driver: parsed .sandbox/test_no_inc.c` — exit 0.

## Root cause

Phase24b shipped `env: ref CTypeEnv` and verified the `ref` lowering
produces `ptr %env` in IR (mangled `_R8CTypeEnv9CBaseType`). That fix
was real but did not address the actual crash: a different
ownership bug in `Heap[T]` semantics.

`base_to_ctype`'s Typedef arm was:

```tml
Typedef(name) => {
    if env.typedefs.has(name) {
        let t: Heap[CType] = env.typedefs.get(name)
        return t.get()
    }
    ...
}
```

`HashMap[Str, Heap[CType]].get(name)` returns the value-type `Heap[CType]`
BY VALUE — a struct copy whose `ptr` field aliases the map bucket's
allocation. Both the returned local `t` and the map's bucket entry
hold the same pointer.

`impl[T] Drop for Heap[T]` (`lib/core/src/alloc/heap.tml:263`) calls
`mem_free(this.ptr)`. When `t` goes out of scope (function return),
the local's drop frees the allocation. The HashMap bucket's pointer
is now dangling. The next call to `env.typedefs.get(name)` returns a
`Heap[CType]` with the freed pointer; `t.get()` dereferences →
SIGSEGV / exit 127.

Why phase24b's `ref CTypeEnv` test (3 sequential calls in a TML test
function) passed: the test runs in `-O0` debug mode where allocator
bucket reuse is slow, so the freed memory often still contained the
expected discriminant byte. Subsequent calls "worked" by reading
freed-but-not-yet-recycled memory. The cc_driver path triggers
enough allocator pressure that the freed buckets get recycled
between calls, surfacing the dangling-pointer crash deterministically.

## Fix

In `compiler-tml/src/cc/types.tml::base_to_ctype`'s Typedef arm,
call `t.into_raw()` on the borrowed Heap after extracting the value:

```tml
Typedef(name) => {
    if env.typedefs.has(name) {
        var t: Heap[CType] = env.typedefs.get(name)
        let r: CType = t.get()
        let _raw: *CType = t.into_raw()
        return r
    }
    return CType::UnresolvedTypedef(name)
}
```

`Heap[T]::into_raw()` nulls `this.ptr` and returns the raw pointer.
The local `t`'s subsequent drop hits the `if this.ptr != null`
guard in the Drop impl and skips `mem_free`, preserving the map
bucket's allocation.

## Known follow-up: same bug class in StructRef/UnionRef/EnumRef arms

`base_to_ctype` has three more arms that return a `Heap[T]` from
the map directly inside an enum constructor:

```tml
StructRef(tag) => {
    if env.structs.has(tag) { return CType::Struct(env.structs.get(tag)) }
    ...
}
```

Here the returned `Heap` flows into the `CType` variant payload.
Whenever the resulting `CType` eventually drops, its `Heap` payload's
drop frees the allocation that the map still references. A
`tml cc` source that uses a `struct Foo` / `union Foo` / `enum Foo`
tag multiple times will exhibit the same crash class.

The pattern is harder to fix at the call site there because the
Heap is moved into the enum constructor and only drops at the
caller's scope end. The proper fix is at the language level:
either give `Heap[T]` Rc-style refcount semantics, or make
`HashMap.get` for Heap-valued maps return a non-owning view (e.g.
`ref Heap[T]` or `*T`).

For now: `tml cc` on C sources without struct/union/enum tag
references works.
