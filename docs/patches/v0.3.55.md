# v0.3.55 — F-013 Refcount Bleed Fix in Shared (ADR-009 B3, phase26b step 1)

**Date:** 2026-07-15 · **Branch:** `fix/era0-stabilization` · **ERA 0, Plan Phase B**

First implementation step of **ADR-009 (Option B3, accepted 2026-07-15)** —
`docs/adr/ADR-009-memory-model-soundness.md`.

## The bug (F-013, confirmed at IR + runtime)

`Shared[T]::increment_count`/`decrement_count` read the refcount by bitwise-copying
the **whole** `SharedInner[T]` into a local (`let inner: SharedInner[T] = *this.ptr`).
On the AST codegen path — the one every `tml build`/`tml run` of a stdlib-importing
program uses — that local's drop-glue called `Shared::drop` on nested handle fields
of the copy, decrementing the REAL nested allocations. Every `duplicate()` of a
`Shared[T]` whose `T` contains nested handles leaked one decrement per handle:
runtime probe showed nested strong_count **2 → 1 → −1**, with the allocation freed
at the 0-crossing while its owner was alive, and subsequent reads returning stale
data from freed memory — **silent** use-after-free, invisible to the test suite
(the test framework compiles via the query/MIR pipeline where this drop is not
elaborated — the tests-vs-production divergence documented in ADR-009).

## The fix

Read the counter through a direct field access (`(*this.ptr).strong_count`) —
the pattern `decrement_count` already used for `weak_count` — so no `SharedInner[T]`
temporary ever exists. IR verified: `increment_count` is now GEP + `load i32` only;
zero `load %struct.SharedInner`, zero drop calls.
