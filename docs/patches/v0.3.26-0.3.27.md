# v0.3.26–0.3.27 — Rust Parity for List Iteration

**Date:** 2026-04-15

## Summary

Two releases that together achieve Rust-equivalent performance for `for x in list`
iteration. TML now generates identical optimized IR to Rust's `for x in vec.iter()`,
including AVX-512 SIMD vectorization with `<8 x i64>` loads.

## Benchmark (10M I64 × 10 iterations, cache-hot, release)

| Language | Avg ops/s | Time | Ratio |
|----------|-----------|------|-------|
| **Rust** (rustc 1.93, O2, `#[inline(never)]`) | 4.57B | 21ms | baseline |
| **TML** (0.3.27, O2) | 4.32B | 23ms | **1.06×** |

The 6% difference is within OS scheduling noise — in some runs TML is faster.

## v0.3.26 — Pointer-Stepping For-In

### Problem
TML `for x in list` called `next() -> Maybe[T]` per iteration, producing a
`{ i32, T }` discriminant + payload struct. The discriminant branch in the loop
body blocked LLVM's LoopVectorizer ("control flow cannot be substituted for a select").
Baseline: 2.6B ops/s vs Rust's 4.5B (1.7× gap).

### Solution
New `gen_for_pointer_stepping` in AST codegen (`loop.cpp`) detects `ListIter`-based
for-in and emits a direct phi-based pointer-stepping loop:

```llvm
pstep.header:
  %ptr = phi ptr [ %init, %preheader ], [ %next, %latch ]
  %done = icmp eq ptr %ptr, %end
  br i1 %done, %exit, %body
pstep.body:
  %val = load i64, ptr %ptr, align 8      ; direct load, no Maybe
  ; ... user body ...
pstep.latch:
  %next = getelementptr inbounds i8, ptr %ptr, i64 %stride
  br %header, !llvm.loop !vectorize
```

### Also in v0.3.26
- Removed unconditional `personality ptr @__CxxFrameHandler3` from MIR functions
  (MIR uses `call` not `invoke`, so personality was unnecessary)
- Loop metadata with `vectorize.enable=true` on pointer-stepping back-edge

## v0.3.27 — @inline + Constant Stride → AVX-512

### Problem
After v0.3.26, the loop structure matched Rust but LLVM couldn't vectorize because:
1. `into_iter()` was opaque — stride was runtime, not constant
2. Allocas couldn't be promoted to SSA (opaque call barrier)

### Solution

**`@inline` on iterator hot path** (`behaviors.tml`):
- `into_iter()` on `impl IntoIterator for List[T]`
- `iter()` on `impl List[T]` — also fixed struct mismatch (4 fields → 3)
- `next()` on `impl Iterator for ListIter[T]`

**Compile-time constant stride** (`loop.cpp`):
- Primitive types: i8=1, i16=2, i32/f32=4, i64/f64/ptr=8
- Struct types: fall back to runtime stride from ListIter field

### Result: Identical Optimized IR

After LLVM O2, the inner loop is 5 instructions — same as Rust:
```llvm
%ptr   = phi ptr [...]
%total = phi i64 [...]
%val   = load i64, ptr %ptr, align 8
%new   = add nsw i64 %val, %total
%next  = getelementptr inbounds nuw i8, ptr %ptr, i64 8  ; constant stride
%done  = icmp eq ptr %next, %end
br i1 %done, %exit, %loop
```

LLVM LoopVectorizer produces:
```llvm
vector.body:
  %wide.load   = load <8 x i64>, ptr %p0, align 8   ; 8 elements (AVX-512)
  %wide.load.1 = load <8 x i64>, ptr %p1, align 8
  %wide.load.2 = load <8 x i64>, ptr %p2, align 8
  %wide.load.3 = load <8 x i64>, ptr %p3, align 8
  ; 4 independent accumulators → 32 elements per iteration
```
