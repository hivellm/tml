# v0.3.71 — Fix `str::replace` K001 dangling ref: bare-name free-function collision (phase27e)

**Date:** 2026-07-17
**Task:** phase27e_generic-free-func-monomorph (K001)

## Summary

Fixes the 5 pre-existing `core/str` K001 failures (`str_coverage2`, `str_advanced`,
`str_transform`, `str_method`, `str_methods`) — all failed LLVM IR parse with
`use of undefined value '@tml_N4core7runtime3mem7replaceE_R1T1T'`, a dangling,
un-monomorphized `core::runtime::mem::replace[T]` callee. **core/str: 27/32 → 33/33**
(32 pre-existing + 1 new regression fixture).

## Root cause (corrected by diagnostic — NOT a monomorphization gap)

phase27e was opened on the hypothesis that the callee was a *generic* module
free-function needing call-site monomorphization (mirror the generic `Type::method`
block at `call_user.cpp:595–632`). A temporary diagnostic at the fallback
(`call_user.cpp:452`) disproved that hypothesis and pinned the real cause:

```
[DIAG-FALLBACK] fn_name=str::replace bare=replace found_mod=core::runtime::mem
                n_param_types=2 func_sig=1 type_params=[] mangled=@tml_N4core7runtime3mem7replaceE_R1T1T
```

`func_sig->type_params` is **empty** — the type checker correctly resolved the callee
as the non-generic `core::str::replace(s, pattern, replacement)` (3 params). The bug
is purely in how the *mangled callee name* is built: the AST-codegen module scan
(`call_user.cpp` ~213–303) locates a module's function by its **bare** name (the
module registry stores functions bare, e.g. `replace`, not `str::replace`). Both
`core::str::replace` (3 params, non-generic) and `core::runtime::mem::replace[T]`
(2 params, generic) share the bare name `replace`, so the scan — iterating an
`unordered_map` — picked `core::runtime::mem` first and mangled the call with **its**
module path and **its** generic `[mut ref T, T]` parameter types (the literal-`T`
`_R1T1T` suffix), producing a callee with no backing definition.

Only the exact bare name `replace` collides: the passing str tests call
`str::replace_first` / `str::replacen` (unique bare names), which resolve correctly —
confirming the collision, not a substitution failure.

## Fix

`compiler/src/codegen/llvm/expr/call_user.cpp` — the module scan now runs a
**two-phase selection** before recording `found_mod_name`/`found_param_types`:

1. **Signature match (primary):** prefer the module whose `FuncSig` matches the
   type-checked `func_sig` — same arity **and** same generic-ness. This
   disambiguates `str::replace` (3 params, non-generic) from
   `core::runtime::mem::replace[T]` (2 params, generic).
2. **Path match (secondary):** prefer a module whose path matches the call's
   qualifier (`str` → `core::str`), or — for bare imported calls — the current
   module being generated.
3. **Fallback:** first match (legacy order) when neither signal fires.

With the correct module selected, the existing registered-symbol lookup
(`call_user.cpp` ~430) resolves `core::str::replace` to its real define; the
declaration-mangling fallback is no longer reached for this call.

The selection only changes behaviour when **multiple** modules expose the same bare
name — the collision case — where it now picks the signature-consistent one
deterministically (also removing the prior `unordered_map`-order nondeterminism).
Single-match resolution is unchanged.

## IR evidence

Emitted IR for `str_method` after the fix:

- `@tml_N4core7runtime3mem7replaceE_R1T1T` (dangling, literal-`T`): **0 occurrences**.
- Call site now `call ptr @tml_N4core3str7replace7replaceE_SSS` (core::str::replace,
  3 `Str` params) — with a **matching `define`**. LLVM parse + verifier clean
  (the suite compiles, links, and executes 33/33).

## Scope boundary — genuine generic free-function monomorphization gap remains

This fixes the **collision** class (the reproducible `core/str` K001s). The
*distinct* latent gap the phase41b fast-path hits — a **genuinely generic** module
free-function call (`func_sig->type_params` non-empty) that misses
`gen_call_generic_func` under a partial bootstrap and reaches the same
declaration-mangling fallback with no queued instantiation — is **not** reproducible
in the current (fast-path-disabled) build and is unchanged here. Its remedy (a
call-site re-mangle + `require_func_instantiation` branch mirroring
`call_user.cpp:595–632` for module free functions) is documented for phase27a /
F-006 fast-path re-enablement. See
`docs/analysis/tooling-performance/04-test-framework-performance.md` (F-006).
