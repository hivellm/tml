# v0.3.73 — Close daemon / ast.bin / meta staleness holes + real cache invalidate (phase42b, F-027..F-030)

**Date:** 2026-07-18 · **Branch:** `fix/era0-stabilization`

## Summary

Four under-invalidation holes let the toolchain serve **stale results** until a cache
directory was manually nuked — and the manual tool (`cache invalidate`) was a stub that
deleted nothing. phase40a made the warm compile daemon central to the agent workflow
(`mcp__tml__check`/`build`/`emit-ir` all route through it), so these were live correctness
hazards, not theoretical. All four are closed; each was reproduced on the pre-fix binary
first (except F-029, whose runtime domain is out of scope — see below).

Scope boundary: this task does **not** touch the incr.bin red-green internals (phase42a).
F-030 only *deletes* a source's incr entries + ir files; it does not restructure them. It
respects phase41c's content-aware `tests.json` invalidation (it never touches
`compiler_hash`, phase41c's global lever).

## F-027 — `.ast.bin` sidecar trusted unconditionally (High, correctness)

**Repro (pre-fix):** a valid `func main` with a *garbage* `r.tml.ast.bin` sidecar failed
`tml build r.tml` with `ast.bin deserialization failed: bad magic` — the sidecar was used
even though the source was newer and valid, with no source-hash/mtime check, bypassing
`force()` so no `ReadSource` dep was recorded and it was re-deserialized every call.

**Fix** (`query_context.cpp`, `query_core.cpp`): the sidecar fast-path moved into the
`provide_parse_module` query provider. It now (a) records the `ReadSource` dependency +
fingerprint (red-green invalidates the parse when the source changes), (b) is served from
the query cache instead of re-deserialized per call, and (c) is used **only when the
sidecar is at least as new as the source** (mtime gate). A corrupt/incompatible sidecar
falls through to a real parse instead of breaking a valid compile. Content-hash validation
is impossible without unfreezing the TML frontend that writes the format
(`lib/std/src/serial/ast.tml`), so mtime is the freshness signal.

## F-028 — daemon result cache keyed on argv mtimes only (Medium-High, correctness)

**Repro (pre-fix):** warm daemon, `TML_DAEMON=1 tml check app.tml` (exit 0, cached), edit an
imported sibling `helper.tml` (not in argv) to introduce a type error, re-run → **stale
exit 0** (cold control correctly reports the error).

**Fix** (`cmd_daemon.cpp`): each cache entry now stores a `universe_epoch` = max mtime over
the transitive source universe (the lib source tree + each argv file's sibling directory);
a warm hit is served only when **both** the argv mtimes **and** the universe epoch are
unchanged. The lib-tree sweep (~2.3k files) is throttled to ≤1×/750 ms to protect the
phase40a warm-latency target; the argv-sibling scan is un-throttled, so project-local
import edits are seen immediately.

## F-029 — daemon meta preload never revalidates (Medium-High → defensive)

**Runtime-confirmation result:** F-029 does **not** affect project-local modules — those are
re-loaded per compile with a source-hash check (`env_module_loading.cpp`), verified: a
result-cache MISS (argv file touched) re-type-checks against the edited sibling. The hole is
**stdlib-only** (`preload_all_meta_caches` was `std::call_once`/process, and
`load_existing_meta_files` short-circuits once `GlobalModuleCache` is populated). A
stale-*result* divergence requires editing a `lib/` source signature under a warm daemon,
which is out of scope (lib/ is a shared tree; editing it is hazardous with concurrent
sessions) — so it was **not independently runtime-reproduced**.

**Fix** (applied because the mechanism is confirmed and the F-028 lib-tree probe now exposes
it): `preload_all_meta_caches` converted from `call_once` to a mutex + resettable guard, plus
`types::reset_meta_caches()` (drops `GlobalModuleCache`, resets the guard). The daemon calls
it on a per-request lib-epoch change (shared probe with F-028) and clears the result cache, so
the recompile-after-change re-preloads fresh interfaces.

## F-030 — `cache invalidate` was a stub (Medium)

**Repro (pre-fix):** `tml cache invalidate <src>` returned exit 0 but deleted nothing (it
substring-matched hash-named files); a `.ast.bin` sidecar survived.

**Fix** (`cmd_cache.cpp`, `testing_test_cache.cpp`): `cache invalidate <src>` now maps a source
to its artifacts across every deterministically-mappable layer and deletes them, **reporting
exactly what was removed to stdout** (visible regardless of log level):

- **`.ast.bin` sidecar** — the `<source>.tml.ast.bin` file beside the source.
- **tests.json + suite EXEs** — new `TestResultCache::invalidate_source()` reverse-looks-up the
  phase-8.5 `source_paths`, deletes matching suites' EXEs (+ `.lib`), drops the entries, and
  re-saves — **without touching `compiler_hash`** (phase41c's lever).
- **incr entries + ir files** — loads `PrevSessionCache`, filters entries by `QueryKey.file_path`,
  deletes `ir/<key>.ll|.libs|.search_paths`, and rewrites `incr.bin` with the survivors.

The content-addressed `run/` and `obj_cache/` layers have no source→artifact backlink and are
self-healing (a changed source hashes differently, so stale entries are never re-hit); they are
reported as reclaimable only via `cache clean --all` — documented, not silently skipped. `cache
info`/`cache clean` now cover the whole cache tree (run/incr/tests/meta + loose files), not just
`cache/run`.

**Verified:** `cache invalidate <hash test>` removed **1 exe + 6 incr entries + 2 ir files**;
`cache info` now shows the real 3.02 GB footprint (incr 2.20 GB).

## Residual caveats

- A library-source edit followed by a warm `check`/`build` within ~750 ms can still see the
  pre-edit stdlib interface (the throttled lib-tree sweep window); the next request past the
  window picks it up. Restart the daemon to force an immediate refresh. Project-local sibling
  edits are immediate.
- Sibling `use` resolution is cwd-relative; the F-028/F-029 CLI checks run the daemon+client
  from the project directory (Windows-only, like `daemon_warm_path.sh`).
