## v0.3.10 — Branchless if-else via LLVM select (phase0h)

**Date:** 2026-04-14  
**Branch:** feat/self-hosting-compiler

---

## Summary

When an `if-else` expression returns the same scalar type from both branches and
neither branch has side effects (literal, identifier, or recursively eligible
nested if-else), the AST codegen now emits a single LLVM `select` instruction
instead of a `br` + label + `phi` triple.

On x86-64, `select i1 %cond, T %a, T %b` compiles to a `CMOV` — a branchless
conditional move that eliminates the branch misprediction penalty entirely.
Chained `if-else-if` expressions produce nested `select` instructions naturally
via recursive `gen_if` codegen.

---

## Changes

### `compiler/src/codegen/llvm/control/if.cpp`

Added two static helper functions:

- **`is_simple_scalar_branch(expr)`** — returns `true` for:
  - Integer, float, or boolean literals
  - Identifier expressions
  - Empty-body blocks wrapping a single eligible expression (`{ expr }`)
  - Nested `if-else` expressions where both branches are also eligible (recursive)

- **`is_scalar_llvm_type(type)`** — returns `true` for `i1`, `i8`, `i16`, `i32`,
  `i64`, `float`, `double`, `ptr`.

In `gen_if`: before emitting labels or branches, if both branches are eligible and
the inferred LLVM types match, emits:

```llvm
%result = select i1 %cond, T %then_val, T %else_val
```

Falls back to the existing `br`+`phi` path whenever:
- Only one branch exists (plain `if` without `else`)
- Either branch has side effects (function calls, assignments, loops, etc.)
- The two branches produce different LLVM types
- The result type is non-scalar (struct, void, etc.)

### Example: 4-arm chained if-else-if

TML source:
```tml
func classify_range(x: I64) -> I64 {
    if x < 25 { 1 } else if x < 50 { 2 } else if x < 75 { 3 } else { 4 }
}
```

Before (br+phi chain):
```llvm
br i1 %cmp1, label %then1, label %else1
; ... 4 basic blocks + 3 phi nodes
```

After (nested selects):
```llvm
%t1 = icmp slt i64 %x, 75
%t2 = select i1 %t1, i64 3, i64 4
%t3 = icmp slt i64 %x, 50
%t4 = select i1 %t3, i64 2, i64 %t2
%t5 = icmp slt i64 %x, 25
%t6 = select i1 %t5, i64 1, i64 %t4
```

## Summary

Verified that the MIR→LLVM emission for value-type struct literals uses
`insertvalue` chains (no alloca round-trip) end-to-end. The analysis
in `docs/analysis/benchmark/05-memory-structs.md` showed a 16-32 ns/op
gap against Rust; this was caused by `memory_bench.tml` benchmarking
`sealed class` heap-allocated types (which correctly use alloca/malloc),
not plain `type` value types.

The MIR path (`emit_struct_init_inst` in `instructions_misc.cpp`, lines
503-563) already emits correct `insertvalue` chains for non-class value
types. The AST path (`gen_struct_expr` in `llvm_struct_expr.cpp`, lines
1030-1166) has the same fast path. No code change was needed.

---

## Verification

### TML emitted IR (`make_point`, debug O0)
```llvm
define internal %struct.Point @tml_make_point(i64 %x, i64 %y) #0 {
  %t3 = insertvalue %struct.Point undef, i64 %t2, 0
  %t5 = insertvalue %struct.Point %t3, i64 %t4, 1
  ret %struct.Point %t5
}
```
No `alloca` for the struct value itself (only `alloca i64` for parameter
ABI, which `mem2reg` eliminates at O1+).

### Rust reference IR (rustc -O, Windows x86-64 MSVC ABI)
```llvm
define internal fastcc void @make_point3d...(ptr %_0) {
  store i64 %x, ptr %_0
  ; ... (sret hidden-pointer pattern)
}
```
Rust uses `sret` on Windows for structs >8 bytes. TML's `insertvalue` is
equivalent at the IR level and better at O0 (no memory traffic).

## v0.3.13 — NRVO in MIR→LLVM sret path

**Date**: 2026-04-14  
**Branch**: feat/self-hosting-compiler  
**Task**: phase0k_nrvo-return-value-opt

---

## Summary

Named Return Value Optimization (NRVO) implemented in the MIR→LLVM codegen path.

When a `sret`-returning function calls another `sret`-returning function and
immediately returns that result, the intermediate alloca+load+store sequence
is eliminated by forwarding `%sret` directly to the callee's hidden sret slot.

**Before (3 instructions):**
```llvm
%sret.slot.0 = alloca %struct.Point, align 8
call void @make_point(ptr sret(%struct.Point) %sret.slot.0, i64 %x, i64 %y)
%v = load %struct.Point, ptr %sret.slot.0, align 8
store %struct.Point %v, ptr %sret, align 8
```

**After (1 instruction):**
```llvm
call void @make_point(ptr sret(%struct.Point) %sret, i64 %x, i64 %y)
```

---

## Implementation

### Pre-scan phase (`mir_codegen.cpp`)
At function entry, a pre-scan over all blocks identifies NRVO candidates:
- Find all `CallInst` results whose callee is in `sret_functions_`
- Check whether any `StoreInst` stores that result to the sret param
- Build `nrvo_call_results_` set (ValueIds eligible for NRVO)

### Emit phase (`instructions_call.cpp` — `emit_sret_call`)
Before allocating the intermediate sret slot, check NRVO eligibility:
- If `inst.result` is in `nrvo_call_results_`, pass `current_func_sret_param_` directly
- Map `cg_values_[result]` to an `Address` pointing at `%sret`
- Return early — no alloca, no load

### Store skip (`instructions.cpp` — `StoreInst` handler)
When an NRVO call result is stored to the sret param, skip the store:
- The write already happened during the call; the store would overwrite with itself
- Guarded by `nrvo_call_results_.count(i.value.id) > 0`

### New per-function state (`mir_codegen.hpp`)
```cpp
bool current_func_has_sret_;
std::string current_func_sret_param_;
mir::ValueId current_func_sret_param_id_;
std::unordered_set<mir::ValueId> nrvo_call_results_;
```

## v0.3.14 — Process-level DLL handle cache + background preload

**Date**: 2026-04-14  
**Branch**: feat/self-hosting-compiler  
**Task**: phase0l_lazy-plugin-dll-loading

---

## Summary

The plugin loader (`compiler/src/plugin/loader.cpp`) gains two performance
improvements:

1. **Process-level DLL handle cache** — `g_dll_cache` is a static
   `unordered_map` keyed by canonical DLL path. After the first
   `LoadLibraryW` succeeds, subsequent `dl_open()` calls for the same path
   return the cached handle in O(1) with no OS call. Stale entries are
   evicted automatically when the file's `mtime` changes (rebuild
   detection), so tests run after a compiler rebuild always load the new DLL.

2. **Background preload** — `Loader::preload_async({"tml_compiler"})` is
   called in `main_launcher.cpp` immediately after the help/version check.
   A detached `std::thread` starts `LoadLibraryW` in the background.
   `Loader::Loader()` calls `wait_preload_done()` which spins until the
   thread completes, so by the time `loader.load("tml_compiler")` executes,
   the DLL is already in `g_dll_cache` — the explicit load is a cache hit.

3. **Segfault fix** — `unload_all()` now evicts the cache entry and calls
   `platform_dl_close()` (bypassing the "skip if cached" check). This
   ensures `DllMain(DLL_PROCESS_DETACH)` fires during controlled teardown
   rather than at `ExitProcess`, eliminating the static-destructor ordering
   crash caused by LLVM's global registries being destroyed in the wrong
   order when the DLL was unloaded by the OS.

---

## Implementation

### New static globals (`loader.cpp`)

```cpp
struct DllCacheEntry {
    void* handle = nullptr;
    fs::file_time_type mtime;
};

static std::mutex g_dll_cache_mutex;
static std::unordered_map<std::string, DllCacheEntry> g_dll_cache;
static std::atomic<int> g_preload_count{0};
```

### `dl_open()` — cache-aware

```cpp
auto Loader::dl_open(const fs::path& path) -> void* {
    std::string key = path.string();
    fs::file_time_type current_mtime = get_path_mtime(path);
    {
        std::lock_guard lock(g_dll_cache_mutex);
        auto it = g_dll_cache.find(key);
        if (it != g_dll_cache.end()) {
            if (it->second.mtime == current_mtime)
                return it->second.handle;          // O(1) — no OS call
            platform_dl_close(it->second.handle);  // stale — evict
            g_dll_cache.erase(it);
        }
    }
    void* handle = platform_dl_open(path);
    if (handle) {
        std::lock_guard lock(g_dll_cache_mutex);
        auto [it, inserted] = g_dll_cache.emplace(key, DllCacheEntry{handle, current_mtime});
        if (!inserted) { platform_dl_close(handle); return it->second.handle; }
    }
    return handle;
}
```

### `dl_close()` — skip FreeLibrary for cached handles

During normal `load()`/`unload()` cycles within a multi-load session, cached
handles are not released (keeps the DLL mapped). `unload_all()` is the
exception — it explicitly evicts from the cache and calls `platform_dl_close`
to trigger controlled DLL detach.

### `Loader::preload_async()` / `wait_preload_done()` (`loader.hpp`)

```cpp
static void preload_async(const std::vector<std::string>& plugin_names);
static void wait_preload_done();
```

`preload_async` spawns a detached thread per unresolved plugin.
`wait_preload_done` spins on `g_preload_count` (500µs sleep per iteration).

### Entry point (`main_launcher.cpp`)

```cpp
// After help/version check — preload only when we need the DLL.
tml::plugin::Loader::preload_async({"tml_compiler"});
tml::plugin::Loader loader;          // constructor calls wait_preload_done()
loader.load("tml_compiler");         // cache hit — no OS call
```

---

## Files Changed

- `compiler/include/plugin/loader.hpp` — added `preload_async` + `wait_preload_done` declarations + `<thread>` include
- `compiler/src/plugin/loader.cpp` — `g_dll_cache` + `g_preload_count` statics, cache-aware `dl_open`, skip-FreeLibrary `dl_close`, evicting `unload_all`, `preload_async`, `wait_preload_done`
- `compiler/src/launcher/main_launcher.cpp` — call `preload_async` after help/version guard

## Performance Note

In the debug build, `tml_compiler.dll` is ~78 MB with statically linked LLVM.

the benchmark gate (<20ms warm) is only achievable in a release build or with
a persistent daemon (phase0n). This task implements the architectural
foundation that phase0n will build on.

## v0.3.16 — Persistent Compilation Daemon

**Date:** 2026-04-14  
**Branch:** feat/self-hosting-compiler

## Summary

Adds `tml daemon start|stop|status` — a persistent background process that
keeps the compiler DLLs and LLVM context warm between invocations.  Second
and subsequent compiles of an unchanged file are served from an in-memory
result cache, bypassing `tml_main()` entirely.

## Changes

### `compiler/src/cli/commands/cmd_daemon.cpp` (new)

- `tml daemon start` — spawns a detached background process, writes
  `.tml-daemon.pid`, enters a Windows named-pipe / Unix domain socket loop.
- `tml daemon stop` — sends a JSON `shutdown` request over the pipe;
  daemon exits cleanly.
- `tml daemon status` — pings the daemon and reports PID + responsive state.
- Auto-shutdown after 30 minutes of inactivity.
- Sequential request handling (LLVM is not thread-safe).
- `TML_DAEMON=1` env var activates forwarding in `tml build/check/run`.

### In-process result cache

- `CacheEntry` stores `(exit_code, stdout, stderr, file_mtime_snapshot)`.
- Key = CRC32c of argv joined with NUL bytes.
- Cache hit: mtime snapshot revalidated against disk (file_time_type comparison).
  If valid, returns cached result without touching `tml_main`.
- Cache miss: runs `tml_main`, stores result.
- Only `check`, `build`, `emit-ir`, `emit-mir` commands are cached (pure
  functions of source files; `run` has side effects and is excluded).

### DLL staleness detection

- Records `tml_compiler.dll` mtime at daemon startup.
- Checked before each request.
- If changed (compiler was rebuilt): clears result cache, sends
  `"daemon: compiler updated, restarting"` response, exits cleanly.
- Next thin-launcher invocation spawns a fresh daemon with the updated DLL.

### `compiler/src/launcher/main_launcher.cpp`

- `try_daemon_forward_launcher()`: thin client runs BEFORE `LoadLibrary`.
  Reads `.tml-daemon.pid` via Win32 `ReadFile` (avoids `std::ifstream >>` hang
  on Windows), connects to the named pipe, writes JSON request, reads response,
  proxies stdout/stderr, returns the daemon's exit code.
- CRC32c computed with canonical `crc32c.hpp` (fixed earlier table divergence).

## Benchmarks (Windows 10, debug build)

| Scenario | Time |
|----------|------|
| Cold (first compile, no daemon) | ~2.9s |
| Warm daemon, first request (cache miss) | 7.7s |
| Warm daemon, second request, no changes (cache hit) | **22ms** |
| `cargo check` incremental no-change (equivalent Rust project) | 98ms |
| Ratio: TML daemon vs `cargo check` | **4.5× faster** |

> **Platform note:** Windows process creation is ~21ms irreducible
> (confirmed: `tml --version` = 22ms).  The <10ms gate is achievable on
> Linux/macOS where `fork` is ~1ms.  The daemon result-cache itself responds
> in <1ms; the remaining 21ms is OS process-creation overhead.

## Compatibility

- No breaking changes. Daemon is opt-in via `TML_DAEMON=1` or explicit
  `tml daemon start`.
- Direct `tml build/check` without `TML_DAEMON` continues to work.

## v0.3.17 — `match` Keyword Helpful Diagnostic

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Users from Rust, Swift, or C# who write `match x { ... }` now get a clear
`error[S001]` diagnostic pointing at the `match` token instead of confusing
cascading parse errors. The parser detects `match` as an identifier, emits
the S001 with a note explaining `when` is the TML equivalent, and skips the
entire braced body to suppress noise.

## Changes

### `compiler/src/parser/parser_expr.cpp`

- In `parse_primary_expr()`: added early check for `Identifier` with lexeme
  `"match"` before the regular identifier path.
- On match: consumes the token, skips the scrutinee + braced body (tracks
  brace depth), then returns `ParseError{code: "S001"}`.
- Result: single clean diagnostic instead of 4+ cascading P001 errors.

### Example

```
error[S001]: 'match' is not valid TML — use 'when' instead
  --> file.tml:3:5
     |
   3 |     match x {
     |     ^^^^
     |
  = note: TML uses 'when' for pattern matching (equivalent to Rust's 'match')
```

## v0.3.19 — File::sync() and File::datasync()

**Date:** 2026-04-15
**Branch:** feat/self-hosting-compiler

## Summary

Adds `File::sync()` and `File::datasync()` methods to the standard library
file module. These guarantee that written data reaches permanent storage,
which is essential for database WAL (Write-Ahead Log) durability, config
file writes, and any safety-critical persistence.

Requested by the UzDB AI agent for their database WAL implementation.

## API

```tml
use std::file::file::File

var f: File = File::open_write("wal.log")
f.write_str("WAL entry 1\n")
f.sync()       // fsync — flush data + metadata to disk
f.datasync()   // fdatasync — flush data only (faster on Linux)
f.close()
```

## Changes

### `lib/std/runtime/file.c`

- `file_sync(TmlFile*)` — calls `fflush()` then:
  - Windows: `_commit(_fileno(handle))`
  - Unix: `fsync(fileno(handle))`
- `file_datasync(TmlFile*)` — calls `fflush()` then:
  - Linux: `fdatasync(fileno(handle))`
  - Windows/macOS: falls back to `fsync()`/`_commit()`

### `lib/std/src/file/file.tml`

- `File::sync() -> Bool` — FFI wrapper for `file_sync`
- `File::datasync() -> Bool` — FFI wrapper for `file_datasync`

## Platform Behavior

| Platform | `sync()` | `datasync()` |
|----------|----------|--------------|
| Windows  | `_commit(fd)` | `_commit(fd)` (no separate fdatasync) |
| Linux    | `fsync(fd)` | `fdatasync(fd)` |
| macOS    | `fsync(fd)` | `fsync(fd)` (no fdatasync on macOS) |
