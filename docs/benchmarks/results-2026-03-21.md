# HTTP Benchmark Results — 2026-03-21

## Environment
- OS: Windows 10 Pro, 32 logical cores
- Tool: bombardier (Go-based HTTP benchmark)
- Duration: 10s per test, 3s warmup
- Debug build (TML), Release (Go/Node)

## Results

| Scenario | TML (thread pool) | Go (net/http) | Node.js (32 cluster) |
|----------|-------------------|---------------|---------------------|
| Plaintext 256c | 25,063 req/s | 17,815 req/s | 138,941 req/s |
| JSON 256c | 12,378 req/s | 11,292 req/s | 104,180 req/s |

| Framework | Avg | Max |

## Analysis

### TML Strengths
- Beats Go on all scenarios (1.4x plaintext, 1.1x JSON, 5.5x single-conn)
- Low single-connection latency (141μs avg)
- Pre-computed response headers (app_build_response)

### TML Weaknesses vs Node
- 5.5x slower on plaintext 256c (25K vs 139K)
- 8.4x slower on JSON 256c (12K vs 104K)
- 173 timeouts at 256c (accept queue saturation)
- Single accept thread → shared mutex queue bottleneck

### Root Causes
1. **Single accept thread**: TML has 1 accept loop distributing to N workers via mutex+condvar queue. Node has 32 independent processes each with their own accept.
2. **Debug build**: TML compiled at O0 with checked arithmetic. Node/Go are release.
3. **Mutex contention**: Shared queue with mutex+condvar limits throughput under high concurrency.
4. **Per-request allocation**: TML allocates response strings per request. Node reuses buffers.

### Recommendations
1. Build TML server in release mode for fair comparison
2. Add SO_REUSEPORT + multiple accept threads (like Node cluster)
3. Use arena allocator for per-request buffers
4. Consider IOCP mode for Windows (already implemented, needs testing)
