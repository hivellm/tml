# Analysis: Code Coverage in TML

**Date**: 2026-04-17
**Scope**: audit of TML's current coverage implementation (`compiler/src/testing/testing_coverage*.cpp`, `lib/test/runtime/coverage.c`, `lib/test/src/coverage.tml`, `compiler/src/cli/commands/cmd_coverage.cpp` — ~3,350 LOC total) and architectural proposal for a rewrite.
**Author**: architect agent (opus, analysis session)

---

## Executive summary

TML currently implements coverage with a **proprietary, function-level** model: the C runtime (`coverage.c`) keeps a lock-free hash table keyed by mangled function names; every instrumented TML function calls `tml_cover_func(name)` on entry. The C++ coordinator (`testing_coverage.cpp` + `testing_coverage_html.cpp`, ~2,550 LOC together) scans source files with ad-hoc hand-written keyword matchers, compares the declared set against the touched set, and emits a monolithic HTML report generated by string concatenation in C++. There is no automatic **line** coverage, no **branch** coverage, and no emission in any ecosystem-standard format (LCOV, Cobertura XML, LLVM `.profraw`). There is zero integration with Codecov, Coveralls, SonarQube or VS Code Coverage Gutters.

Over the past ten years the industry has converged on **two substrates**: (1) LLVM source-based coverage (`-fprofile-instr-generate -fcoverage-mapping` → `.profraw` → `llvm-profdata merge` → reports) and (2) the textual **LCOV** `.info` format as the interoperability lingua franca. Almost every modern tool (`cargo-llvm-cov`, `grcov`, `c8`, `coverage.py`, Jest/Vitest, Coverlet) can emit LCOV, and every SaaS ingests it.

**Primary recommendation**: drop the proprietary schema and adopt **LLVM source-based coverage as the single backbone for both C++ and TML**. TML already uses Zig CC (Clang 20) and LLVM 22.1 (ADR-007); the native toolchain is present. Emit `.profraw` from the C++ compiler (via `-fprofile-instr-generate`) and from TML binaries (by injecting `llvm.instrprof.increment` intrinsics in MIR→IR, replacing the hand-rolled instrumentation). Merge with `llvm-profdata merge`, export LCOV and JSON with `llvm-cov export`. The HTML report stops being a C++ file and becomes a **static SPA** (compact JSON + vanilla JS) at roughly 10% of the current C++ cost.

**Estimated impact**: from ~3,350 LOC down to ~800 LOC (a ~76% reduction). Gains: line + branch + MC/DC granularity, native Codecov/Coveralls/Sonar compatibility, PR diff coverage, VS Code Coverage Gutters support. Losses: the 1,397-line HTML-in-C++ and the 1,153-line regex-like scanner that duplicates the parser.

## Key findings (what the audit revealed)

1. **The task statement overestimates current granularity.** The request says the compiler injects `__tml_cov_hit(file_id, line)` per line. In reality, the codegen emits `tml_cover_func(const char* name)` calls (see `lib/test/runtime/coverage.c:134`) — **function-level, not line-level**. The `cover_line`/`cover_branch` APIs exist in `coverage.tml` but are manual; neither is automatically emitted by the codegen. This must be corrected before any plan is built on the old assumption.

2. **Zero ecosystem compatibility.** Output today is an ad-hoc JSON plus an auto-generated HTML. No connection to Codecov, Coveralls, SonarQube, IDE extensions (VS Code Coverage Gutters), or converters like `grcov`/`llvm-cov export`. The moment "line coverage" is added, rebuilding LCOV from scratch is the real work — skipping LLVM's output means reinventing it.

3. **The HTML layer is the most expensive and the most replaceable.** `testing_coverage_html.cpp` is 1,397 LOC emitting string-by-string HTML+CSS+JS. This is exactly the class of code the industry solved with templates (Jinja in coverage.py, Handlebars in grcov, React-precompiled in Istanbul) or with static SPAs (modern llvm-cov, ReportGenerator). The correct refactor: emit **compact JSON** (LCOV-derived) and ship a **static SPA** (`coverage.html` + `coverage.json` + `app.js`) built once.

4. **The LLVM toolchain is already available.** TML depends on LLVM 22.1 at `F:/LLVM` (ADR-007 Zig CC). `llvm-profdata`, `llvm-cov`, and the `compiler-rt` profile runtime are already bundled. This is not a new vendor; it is using what is already shipped.

5. **OpenCppCoverage is not the right long-term pick.** It is Windows-only, PDB/DbgHelp-based, with 100–300% overhead (hardware breakpoints / debug-trap patching). Acceptable as a stop-gap for the C++ compiler binary today, but not a cross-platform strategy.

6. **Function-level is unacceptable in 2026.** Every SaaS, IDE and PR reviewer expects **line + branch** coverage (and ideally MC/DC). Keeping the current model loses adoption immediately once TML is used in non-toy projects.

---

## Recommendation in one paragraph

Adopt LLVM source-based coverage as the single standard: instrument the TML codegen to emit `llvm.instrprof.increment` intrinsics and `__llvm_coverage_mapping` per function following the InstrProfiling spec (documented in `llvm/lib/ProfileData/InstrProf.cpp` and `clang/docs/SourceBasedCodeCoverage.rst`); produce one `default.profraw` per execution; merge with `llvm-profdata merge`; export LCOV via `llvm-cov export -format=lcov` and JSON via `llvm-cov export -format=text`; generate HTML via a static SPA that consumes the exported JSON. For the C++ compiler, enable `-fprofile-instr-generate -fcoverage-mapping` in the Zig CC build. Delete `testing_coverage_html.cpp` (1,397 LOC) and rewrite `testing_coverage.cpp` as a thin LCOV→JSON+SPA driver (~300 LOC).

## Suggested next step

Open the task `phase-coverage-llvm-migration` with three visible phases in `proposal.md`:

1. **Spike (1–2 days)**: build `compiler/` with `-fprofile-instr-generate` via Zig CC, run the test runner, extract `.profraw`, generate `coverage.lcov` with `llvm-cov export`. Validate the LLVM ecosystem works end-to-end **before** touching the TML codegen.
2. **TML instrumentation (≤1 week)**: replace `tml_cover_func` emission with `llvm.instrprof.increment` intrinsics in the MIR→IR builder; emit `__llvm_coverage_mapping` sections per function. Remove `tml_cover_func` and friends from `coverage.c`.
3. **New report (≤1 week)**: delete `testing_coverage_html.cpp`; create `compiler/src/testing/coverage_report/` with `template.html` + `app.js` + an LCOV→JSON converter (~200 LOC in C++ or TML consuming `lib/std/io`).

Keep `tml test --coverage` as the user-facing entry point; internally it now calls `llvm-profdata merge` + `llvm-cov export` + the SPA packer.
