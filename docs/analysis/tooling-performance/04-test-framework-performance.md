# 04 — Test Framework Performance (The Dominant Cost)

**F-005 — RESOLVED (phase41a, 2026-07-17) — Default test mode compiled ONE native EXE per test file.**
Evidence (original): `cmd_test.hpp:170` (`suite_mode = false` default) → `cmd_test.cpp:293` (`max_per_suite = (coverage || !suite_mode) ? 1 : 10`) → `group_into_suites(..., 1)`. Full-run discovery is **2066 files / 131 groups** (the "1339 `*.exe`" cache count was stale). The aggregated model already existed — `--suite-mode` and `--unified` — but neither was default.
Impact: **Very High** — the single largest test-time multiplier (link steps + process spawns). Confidence: **High**.
**Resolution:** aggregation is now the default for non-coverage runs (`suite_mode=true`, **25 files/EXE**); `--coverage` and the new `--no-suite` flag force per-file. Full-run link/codegen cycles: **2066 → 176 suites = 11.7×** reduction; measured 14× on `lib/core/tests/hash` (14 exes → 1). `--unified` was disqualified as default (no result cache; link failure exits 0 with zero tests = silent loss). Correctness preserved: aggregated compile-failure isolates the offending file as SKIP while siblings still compile/run; a crashing/timing-out test is attributed as the offender and never-started siblings are re-run individually (no silent loss); NDJSON per-test events now carry the original test index (fixed a misattribution when compile-failed files leave gaps). A latent `lld-link: duplicate symbol: __tml_register_routes` (HTTP route-registration + `__tml_route_thunk_N` emitted with external linkage in every test obj) was the blocker for any multi-file link and is fixed (internal linkage under `force_internal_linkage`). Parity verified: `test_aggregation.sh` 16/16, `core/hash` 14/14 identical in both modes. See CHANGELOG v0.3.69.

**F-006 — The stdlib codegen-state fast-path is DISABLED; every test file re-emits the entire stdlib. — phase41b ROOT-CAUSED (reproduced); enablement DEFERRED to phase27a K001 + a bootstrap redesign.**
Evidence: `testing_compile_parallel.cpp:41–43` — the `build_stdlib_object(config)` call is commented out ("cached state causes codegen issues: I32::duplicate redefinition … i64/i32 type mismatches"). Because `g_stdlib_codegen_state` stays null, `compile_suite` (`testing_compile.cpp:623–628`) falls to `qopts.incremental=true` and runs `emit_module_pure_tml_functions()` for **all ~5000 functions across 287 modules** per test file.
Impact: **Very High** — redundant full-stdlib codegen multiplied by 1339. Confidence: **High**.

**phase41b root-cause (reproduced with evidence, 2026-07-17).** Re-enabling `build_stdlib_object` on a scratch build made the fast path engage on a *minimal* bootstrap (`use core::hash` + `use std::collections`; state captured in 20 s, 1235 KB IR) and **every** test object *and the shared stdlib object itself* failed identically:
`[K001] Failed to parse LLVM IR: use of undefined value '@tml_N4core7runtime3mem7replaceE_R1T1T'`.
That mangled callee is `core::runtime::mem::replace` with a **literal `T`** (the un-monomorphized generic template), even though `mem::replace[T]` is defined (`lib/core/src/runtime/mem.tml:205`). Traced to `call_user.cpp:452`: generic **module free-function** calls have no call-site re-mangle+queue branch (generic **`Type::method`** calls do — `call_user.cpp:595–632`), so when `gen_call_generic_func` misses (its `pending_generic_funcs_` lookup fails when the callee's module isn't fully registered — e.g. a partial bootstrap), the call falls to the declaration-name fallback and emits the template symbol with no queued definition → dangling ref. **This is the SAME error as the pre-existing 5× `core/str` K001 failures** (`str_coverage2/advanced/transform/method/methods`), which reproduce identically in the CURRENT slow path — i.e. the underlying defect is a phase27a K001-family generic-substitution root, not a fast-path-only bug. Full enablement additionally requires: (1) a **per-suite-scoped, complete** bootstrap — the monolithic `test_bootstrap.tml` imports ~12 *phantom* `pub mod` modules declared in `lib/core/src/mod.tml` without source files (`core::mem`/`clone`/`cmp`/`convert`/`marker`/`pin`/`error`/`any`/`tuple`/`ringbuf`, `std::datetime`/`glob`) so its typecheck aborts, and a partial bootstrap yields dangling refs like the above; (2) capturing `generated_impl_methods_output_`/`generated_impl_methods_` in `CodegenLibraryState` (currently only `generated_functions_` is captured — `llvm_ir_gen_generics.inc:61,66`; restore at `generate.cpp:705–707`) to avoid the "I32::duplicate redefinition" local-vs-cached collision; (3) resolving the i64/i32 range-iterator width (phase27a K001 Class 2); and (4) overcoming eager full-stdlib codegen slowness (an all-loadable-modules bootstrap timed out **>500 s** just building the object — the code's own note at `generate.cpp:419` about hanging). Minimal in-scope path landed in phase41b: **F-012** (below). Remaining work is proposed as phase27a (K001 free-function + range monomorphization) plus a per-suite-scoped shared-object redesign of `build_stdlib_object`.

**F-007 — Each test object embeds full internal-linkage stdlib (`library_decls_only=false`). — blocked behind F-006.**
Evidence: `testing_compile.cpp:995` ("each test .obj has full library defs (internal linkage)"); `testing_compile_parallel.cpp:219–224`. Consequence: every single-test EXE ~345 KB with the whole stdlib duplicated (measured: `compiler_borrow_closure_capture.exe` = 345 600 B; 1518 cached EXEs / 756 MB), heavy per-EXE link. Rooted in the same LLD multiple-definition issue that blocks F-006, and gated behind the same phase27a K001 + bootstrap-redesign work (decls-only test objects require a complete, defined-once shared object).
Impact: **High** (bloats link + disk, blocks shared-stdlib linking). Confidence: **High**.

**F-008 — Per-file codegen inside a suite is forced single-threaded. (PARTIALLY ADDRESSED, phase41a)**
Evidence: `testing_compile.cpp` historically hardcoded `int num_compile_threads = 1;` ("avoid LLVM global state corruption"). Parallelism only existed at suite level (≤8, `testing_compile_parallel.cpp`).
phase41a: `compile_suites_parallel` now hands its idle worker budget to intra-suite codegen threads (`CompileConfig::intra_suite_threads`, workers × intra ≤ 8 — the same global envelope suite-level parallelism always used). Targeted runs with few aggregated suites keep parallel codegen; full runs keep the historical 8×1. REMAINING: when suite-count ≥ worker-count, a 25-file chunk with heavy-generics files is a long serial critical path (measured: `std_stream_1` 779 s cold).
Impact: **Medium**. Confidence: **High**.

**F-009 — Each file spawns a detached watchdog thread with 60 s timeout + 100 ms polling.**
Evidence: `testing_compile.cpp:645–668`. Thread create/detach per file plus coarse 100 ms poll granularity adds latency and thread churn across 1339 files.
Impact: **Low–Medium**. Confidence: **High**.

**F-010 — Incremental-cache saves serialize all suite workers on a global mutex.**
Evidence: `testing_compile.cpp:58` `g_incr_cache_mutex`, used at `707–711` around `save_incremental_cache`. When the stdlib fast-path is off (the current default, F-006), incremental is ON and every file's cache write serializes the otherwise-parallel workers on `incr.bin` disk I/O.
Impact: **Medium**. Confidence: **High**.

**F-011 — Subprocess-per-suite execution; each test EXE loads ~100 MB of runtime DLLs. (MITIGATED by F-005 resolution, phase41a)**
Evidence: `testing_coordinator.cpp` exec loop; `cmd_test.cpp` ("each EXE loads ~100MB of runtime DLLs"). Windows process creation ≈21 ms per spawn, plus DLL load per process.
phase41a: full-run subprocess count drops with the link count (2066 → ~176 `--run-all` processes, +1 per crash/timeout re-run) — ~12× fewer spawns/DLL loads. The per-spawn cost itself (in-process execution, shared runtime) remains future work.
Impact: was **Medium–High**, now **Low–Medium**. Confidence: **High**.

**F-012 — LLVM backend re-initialized on every object compilation. — RESOLVED (phase41b, 2026-07-17).**
Evidence (original): `object_compiler.cpp:269–274` — `compile_ir_string_to_object` constructed a fresh `LLVMBackend` and called `initialize()` each call, i.e., per test file (and per dispatcher), creating+disposing an `LLVMContext` every time.
**Resolution:** `compile_ir_string_to_object` and `compile_ir_string_to_buffer` now obtain the backend from `get_thread_local_llvm_backend()` (`object_compiler.cpp`), which constructs and `initialize()`s exactly one `LLVMBackend` per worker thread and reuses it (and its `LLVMContext`) across every object compilation on that thread. LLVM target init was already process-global (`std::call_once` inside `initialize()`); the eliminated cost was the per-object context lifecycle. The context is safe to reuse: each call parses its IR into a fresh module and disposes that module after emitting, so no module state leaks. Behaviour is transparent (identical object bytes). Parity verified on clean suites with zero divergence: `core/hash` 14/14, `compiler/borrow` 12/12, `core/str` = the same 5 pre-existing K001 `mem::replace` failures, `core/alloc` 43/44 (the one miss, `shared_sync_edge`, is a pre-existing flaky concurrency test that passes 1/1 in isolation). Determinism gate (10×, adversarial allocator) pure-TML sentinels unchanged.
Impact: **Medium**. Confidence: **High**.

**F-013 — Redundant per-file source scans (imports detected by re-reading files 2–3×).**
Evidence: `testing_compile.cpp:909–962` (read first 30 lines for registry synth), again in `get_runtime_objects`, and `1175–1263` (full-file re-read for `use <pkg>::` / build.tml). Repeated I/O per suite.

**F-014 — Result cache is fragile: content-hash + "all-passed" + whole-DLL compiler hash → rarely reused.**
Evidence: `testing_test_cache.cpp` — `is_cached` requires `all_passed` and exact `source_hashes` match; `compute_compiler_hash` fingerprints the 71 MB DLL (mtime:size), so any compiler rebuild → `invalidate_all_exes()` (coordinator line ~1015). `tests.json` currently 618 bytes confirms near-zero population.
Impact: **High** (the cache that should make reruns cheap is effectively cold). Confidence: **High**.
