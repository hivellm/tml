# 04 — Test Framework Performance (The Dominant Cost)

**F-005 — RESOLVED (phase41a, 2026-07-17) — Default test mode compiled ONE native EXE per test file.**
Evidence (original): `cmd_test.hpp:170` (`suite_mode = false` default) → `cmd_test.cpp:293` (`max_per_suite = (coverage || !suite_mode) ? 1 : 10`) → `group_into_suites(..., 1)`. Full-run discovery is **2066 files / 131 groups** (the "1339 `*.exe`" cache count was stale). The aggregated model already existed — `--suite-mode` and `--unified` — but neither was default.
Impact: **Very High** — the single largest test-time multiplier (link steps + process spawns). Confidence: **High**.
**Resolution:** aggregation is now the default for non-coverage runs (`suite_mode=true`, **25 files/EXE**); `--coverage` and the new `--no-suite` flag force per-file. Full-run link/codegen cycles: **2066 → 176 suites = 11.7×** reduction; measured 14× on `lib/core/tests/hash` (14 exes → 1). `--unified` was disqualified as default (no result cache; link failure exits 0 with zero tests = silent loss). Correctness preserved: aggregated compile-failure isolates the offending file as SKIP while siblings still compile/run; a crashing/timing-out test is attributed as the offender and never-started siblings are re-run individually (no silent loss); NDJSON per-test events now carry the original test index (fixed a misattribution when compile-failed files leave gaps). A latent `lld-link: duplicate symbol: __tml_register_routes` (HTTP route-registration + `__tml_route_thunk_N` emitted with external linkage in every test obj) was the blocker for any multi-file link and is fixed (internal linkage under `force_internal_linkage`). Parity verified: `test_aggregation.sh` 16/16, `core/hash` 14/14 identical in both modes. See CHANGELOG v0.3.69.

**F-006 — The stdlib codegen-state fast-path is DISABLED; every test file re-emits the entire stdlib. — phase41b ROOT-CAUSED (reproduced); enablement DEFERRED to phase27a K001 + a bootstrap redesign.**
Evidence: `testing_compile_parallel.cpp:41–43` — the `build_stdlib_object(config)` call is commented out ("cached state causes codegen issues: I32::duplicate redefinition … i64/i32 type mismatches"). Because `g_stdlib_codegen_state` stays null, `compile_suite` (`testing_compile.cpp:623–628`) falls to `qopts.incremental=true` and runs `emit_module_pure_tml_functions()` for **all ~5000 functions across 287 modules** per test file.
Impact: **Very High** — redundant full-stdlib codegen multiplied by 1339. Confidence: **High**.

**phase27e update (2026-07-17, v0.3.71): the `core/str` K001 class was a DIFFERENT root than assumed — a bare-name COLLISION, now RESOLVED.** A temporary diagnostic at `call_user.cpp:452` disproved the "generic free-function needs monomorphization" reading of the 5 `core/str` failures: `func_sig->type_params` is **empty** — the type checker resolved the callee as the non-generic `core::str::replace` (3 params). The dangling `@tml_N4core7runtime3mem7replaceE_R1T1T` came from the AST-codegen module scan picking the WRONG module for the *mangled name*: the registry stores functions by BARE name, and `core::str::replace` (3 params) and `core::runtime::mem::replace[T]` (2 params, generic) share bare `replace`; the `unordered_map`-order scan chose `core::runtime::mem` and mangled with its generic `[mut ref T, T]` params. Fixed in `call_user.cpp` (~213–303) by a two-phase module selection preferring the module whose `FuncSig` matches the type-checked signature. **core/str 27/32 → 33/33.** So the 5 `core/str` K001s are NOT the same defect as the fast-path's genuinely-generic `mem::replace[T]` miss below — they only shared the symptom symbol name. The fast-path's genuine free-function monomorphization gap (blocker (1) below) is still open and requires the `require_func_instantiation` call-site branch; it is not reproducible in the current (fast-path-disabled) build.

**phase41b root-cause (reproduced with evidence, 2026-07-17).** Re-enabling `build_stdlib_object` on a scratch build made the fast path engage on a *minimal* bootstrap (`use core::hash` + `use std::collections`; state captured in 20 s, 1235 KB IR) and **every** test object *and the shared stdlib object itself* failed identically:
`[K001] Failed to parse LLVM IR: use of undefined value '@tml_N4core7runtime3mem7replaceE_R1T1T'`.
That mangled callee is `core::runtime::mem::replace` with a **literal `T`** (the un-monomorphized generic template), even though `mem::replace[T]` is defined (`lib/core/src/runtime/mem.tml:205`). Traced to `call_user.cpp:452`: generic **module free-function** calls have no call-site re-mangle+queue branch (generic **`Type::method`** calls do — `call_user.cpp:595–632`), so when `gen_call_generic_func` misses (its `pending_generic_funcs_` lookup fails when the callee's module isn't fully registered — e.g. a partial bootstrap), the call falls to the declaration-name fallback and emits the template symbol with no queued definition → dangling ref. **[phase27e correction, v0.3.71]** this shares the *symptom symbol* with the 5× `core/str` K001 failures (`str_coverage2/advanced/transform/method/methods`) but is a **DIFFERENT root**: those were a bare-name module-scan collision (`str::replace` → `core::runtime::mem::replace`, `func_sig` non-generic), now RESOLVED (see phase27e update above). The fast-path case here is the *genuinely-generic* miss — `func_sig->type_params` non-empty, `gen_call_generic_func` fails under a partial bootstrap — and still needs the call-site re-mangle+queue branch. It is a phase27a K001-family generic-substitution root, only reproducible under the (disabled) fast-path. Full enablement additionally requires: (1) a **per-suite-scoped, complete** bootstrap — the monolithic `test_bootstrap.tml` imports ~12 *phantom* `pub mod` modules declared in `lib/core/src/mod.tml` without source files (`core::mem`/`clone`/`cmp`/`convert`/`marker`/`pin`/`error`/`any`/`tuple`/`ringbuf`, `std::datetime`/`glob`) so its typecheck aborts, and a partial bootstrap yields dangling refs like the above; (2) capturing `generated_impl_methods_output_`/`generated_impl_methods_` in `CodegenLibraryState` (currently only `generated_functions_` is captured — `llvm_ir_gen_generics.inc:61,66`; restore at `generate.cpp:705–707`) to avoid the "I32::duplicate redefinition" local-vs-cached collision; (3) resolving the i64/i32 range-iterator width (phase27a K001 Class 2); and (4) overcoming eager full-stdlib codegen slowness (an all-loadable-modules bootstrap timed out **>500 s** just building the object — the code's own note at `generate.cpp:419` about hanging). Minimal in-scope path landed in phase41b: **F-012** (below). Remaining work is proposed as phase27a (K001 free-function + range monomorphization) plus a per-suite-scoped shared-object redesign of `build_stdlib_object`.

**F-007 — Each test object embeds full internal-linkage stdlib (`library_decls_only=false`). — blocked behind F-006.**
Evidence: `testing_compile.cpp:995` ("each test .obj has full library defs (internal linkage)"); `testing_compile_parallel.cpp:219–224`. Consequence: every single-test EXE ~345 KB with the whole stdlib duplicated (measured: `compiler_borrow_closure_capture.exe` = 345 600 B; 1518 cached EXEs / 756 MB), heavy per-EXE link. Rooted in the same LLD multiple-definition issue that blocks F-006, and gated behind the same phase27a K001 + bootstrap-redesign work (decls-only test objects require a complete, defined-once shared object).
Impact: **High** (bloats link + disk, blocks shared-stdlib linking). Confidence: **High**.

**F-008 — Per-file codegen inside a suite is forced single-threaded. (PARTIALLY ADDRESSED, phase41a; phase41c: still blocked, documented)**
**phase41c (2026-07-17, v0.3.72):** NOT raised further. phase41b deferred the codegen-state restructuring (F-006 root-caused but not landed — the LLVM global-state / `g_stdlib_codegen_state` fast-path stays off), so the constraint forcing per-file codegen single-threaded is unchanged since phase41a. Raising per-file parallelism > 1 without that restructuring risks LLVM global-state corruption; per the task's correctness bias it is left as-is. `intra_suite_threads` (phase41a) still hands idle suite-worker budget to intra-suite codegen on targeted runs.

Evidence: `testing_compile.cpp` historically hardcoded `int num_compile_threads = 1;` ("avoid LLVM global state corruption"). Parallelism only existed at suite level (≤8, `testing_compile_parallel.cpp`).
phase41a: `compile_suites_parallel` now hands its idle worker budget to intra-suite codegen threads (`CompileConfig::intra_suite_threads`, workers × intra ≤ 8 — the same global envelope suite-level parallelism always used). Targeted runs with few aggregated suites keep parallel codegen; full runs keep the historical 8×1. REMAINING: when suite-count ≥ worker-count, a 25-file chunk with heavy-generics files is a long serial critical path (measured: `std_stream_1` 779 s cold).
Impact: **Medium**. Confidence: **High**.

**F-009 — Each file spawns a detached watchdog thread with 60 s timeout + 100 ms polling. — POLL ELIMINATED (phase41c, 2026-07-17, v0.3.72).**
Evidence (original): `testing_compile.cpp:645–668`. Thread create/detach per file plus coarse 100 ms poll granularity adds latency and thread churn across 1339 files.
**Resolution:** the worker now waits on a `condition_variable` (`wait_until` with the same 60 s deadline) instead of polling a flag every 100 ms — it wakes the instant codegen signals done, removing up to 100 ms of dead latency per file between completion and the next poll tick. The codegen still runs on its own thread (LLVM cannot be safely interrupted; on timeout the thread is abandoned/detached), so a shared timer wheel would not remove the per-file thread — only the (now-eliminated) polling. The thread-per-file is inherent to the F-008 single-threaded-codegen safety model.
Impact: **Low–Medium**. Confidence: **High**.

**F-010 — Incremental-cache saves serialize all suite workers on a global mutex. — BATCHED (phase41c, 2026-07-17, v0.3.72).**
Evidence (original): `testing_compile.cpp:58` `g_incr_cache_mutex`, used around per-file `save_incremental_cache`. When the stdlib fast-path is off (the current default, F-006), incremental is ON and every file's cache write serialized the otherwise-parallel workers on `incr.bin` disk I/O — an O(files) load-merge-rewrite of the whole file under one global lock.
**Resolution:** each file now folds its recorded incremental entries into a per-suite in-memory accumulator (`query::IncrCacheWriter`) under a cheap *suite-local* mutex; the suite flushes `incr.bin` exactly once after its file loop, holding `g_incr_cache_mutex` for a single load-merge-write. Cross-suite serialization collapses from O(files) to O(suites). New surface: `QueryContext::merge_incremental_into(IncrCacheWriter&)` + `IncrCacheWriter::merge_from_writer(...)` — format-preserving, does not alter the incr.bin layout or red-green semantics (that is phase42a's domain). The heavy IR/link payloads were already written per file during `codegen_unit()`; only lightweight entry metadata is accumulated.
Impact: **Medium**. Confidence: **High**.

**F-011 — Subprocess-per-suite execution; each test EXE loads ~100 MB of runtime DLLs. (MITIGATED by F-005 resolution, phase41a)**
Evidence: `testing_coordinator.cpp` exec loop; `cmd_test.cpp` ("each EXE loads ~100MB of runtime DLLs"). Windows process creation ≈21 ms per spawn, plus DLL load per process.
phase41a: full-run subprocess count drops with the link count (2066 → ~176 `--run-all` processes, +1 per crash/timeout re-run) — ~12× fewer spawns/DLL loads. The per-spawn cost itself (in-process execution, shared runtime) remains future work.
Impact: was **Medium–High**, now **Low–Medium**. Confidence: **High**.

**F-012 — LLVM backend re-initialized on every object compilation. — RESOLVED (phase41b, 2026-07-17).**
Evidence (original): `object_compiler.cpp:269–274` — `compile_ir_string_to_object` constructed a fresh `LLVMBackend` and called `initialize()` each call, i.e., per test file (and per dispatcher), creating+disposing an `LLVMContext` every time.
**Resolution:** `compile_ir_string_to_object` and `compile_ir_string_to_buffer` now obtain the backend from `get_thread_local_llvm_backend()` (`object_compiler.cpp`), which constructs and `initialize()`s exactly one `LLVMBackend` per worker thread and reuses it (and its `LLVMContext`) across every object compilation on that thread. LLVM target init was already process-global (`std::call_once` inside `initialize()`); the eliminated cost was the per-object context lifecycle. The context is safe to reuse: each call parses its IR into a fresh module and disposes that module after emitting, so no module state leaks. Behaviour is transparent (identical object bytes). Parity verified on clean suites with zero divergence: `core/hash` 14/14, `compiler/borrow` 12/12, `core/str` = the same 5 pre-existing K001 `mem::replace` failures, `core/alloc` 43/44 (the one miss, `shared_sync_edge`, is a pre-existing flaky concurrency test that passes 1/1 in isolation). Determinism gate (10×, adversarial allocator) pure-TML sentinels unchanged.
Impact: **Medium**. Confidence: **High**.

**F-013 — Redundant per-file source scans (imports detected by re-reading files 2–3×). — SINGLE-PASS (phase41c, 2026-07-17, v0.3.72).**
Evidence (original): `testing_compile.cpp:909–962` (read first 30 lines for registry synth) and `1175–1263` (full-file re-read for `use <pkg>::` / build.tml). Repeated I/O per suite.
**Resolution:** each test file's `use` imports are scanned exactly once up front into a per-file `TestImportScan { use_lines, package_names }`; both the conditional-runtime registry synthesis (matches `use std::*` prefixes against `import_module_map`) and the external-package build.tml detection (`use <pkg>::`) now consume that struct instead of reopening the file. One `getline` pass per test file replaces the previous 2–3. Behaviour is a superset of the old (whole-file scan vs first-30-lines; comment lines skipped consistently) — verified zero result divergence on clean suites.
Impact: **Low–Medium**. Confidence: **High**.

**F-014 — Result cache is fragile: content-hash + "all-passed" + whole-DLL compiler hash → rarely reused. — FIXED (phase41c, 2026-07-17, v0.3.72).**
Evidence (original): `testing_test_cache.cpp` — `compute_compiler_hash` fingerprinted the 71 MB DLL by **mtime:size**, so any compiler rebuild — or even a `touch` — changed the key and the coordinator's `invalidate_all_exes()` (`testing_coordinator.cpp` ~1039) wiped every entry's `all_passed`+`exe_path`. Since compiler development (frequent rebuilds) is the dominant workflow, the cache was cold on the first run after every build. A second, distinct defect: `--no-cache` (and any filtered run) called `cache.save()` on an **unloaded** map, so a `--no-cache` single-suite run overwrote `tests.json` down to just that suite, discarding every sibling's cached result.
**Root cause (measured, 2026-07-17):** with the pre-fix binary, `touch tml_compiler.dll` (mtime change, byte-identical content) then rerun `compiler/borrow` logged `Compiler/runtime changed — invalidating all cached EXEs` and took **17.1 s** (full recompile) vs **0.5 s** cached. A `--no-cache` single-suite run reduced a 319-entry `tests.json` to 1 entry.
**Resolution:** (1) `compute_compiler_hash` is now **content-aware** — `tml::VERSION` + CRC32C of the DLL *content* (+ size), memoised once per process. A no-op relink / `touch` yielding byte-identical output keeps the cache warm; any real codegen change still invalidates (correctness bias: content differs ⇒ invalidate). (2) The coordinator now **always loads** the existing cache before partitioning — even in `--no-cache` mode — so `save()` preserves untouched suites; `--no-cache` only disables *using* the cache to skip work. Verified: post-touch rerun stays `is cached (passed, skipping)` at **1.9 s**; a `--no-cache` run on one of three cached suites keeps all three; second consecutive runs of `core/hash`/`compiler/borrow`/`std/json` drop to **~1.8 s** (from 18–49 s cold) with zero result divergence. "Cache what passed, recheck what failed" is preserved (`is_cached` still gates on `all_passed`; `get_reusable_exe` still reuses an unchanged EXE for a suite that failed).
Impact: **High** (the cache that should make reruns cheap is now warm across rebuilds). Confidence: **High**.
